# Lola LMS — правила репозитория

Мультитенантная SaaS-LMS. Полное ТЗ — в `docs/`. Перед любой задачей читать
`docs/00-overview.md` и раздел `docs/`, который описывает затрагиваемый модуль.

## Стек
Nuxt 3 (SSR) + Nitro, TypeScript, Postgres 16 + pgvector, Drizzle ORM, pg-boss, S3 (MinIO),
Tailwind с токенами бренд-бука Lola, Vitest + Playwright.

## Незыблемые правила
1. **RLS.** Каждая таблица с `tenant_id` имеет политику изоляции. Новая таблица без политики —
   падает тест `tests/integration/rls.spec.ts`. Тенант берётся из сессии, никогда из тела запроса.
2. **Доступ к БД только через `withTenant(tenantId, userId, fn)`.** Прямой вызов драйвера запрещён.
3. **Сервер считает, клиент показывает.** Прогресс, баллы, доступность урока — на сервере.
4. **Попытка теста иммутабельна.** Снапшот пишется при старте и не меняется.
5. **Схема меняется только миграцией.** Руками в БД не лезть, откат — новой миграцией.
6. **Логика в `server/services`**, эндпоинт тонкий: валидация → сервис → сериализация.
7. **Контракты — zod в `shared/schemas`**, один источник для клиента и сервера.
8. **Тексты — через i18n.** Хардкод строк в компонентах запрещён. Язык по умолчанию — `uk`.
9. **Стили — только токены** бренд-бука (беж фон, солнце = действие, бирюза = результат,
   коралл = ошибка). Магических цветов и отступов нет.
10. **Секретов в репозитории нет.** Только `.env.example`.
11. **Правила прохождения — в назначении, не в контенте.** В таблицах и схемах контента
    не должно быть `attempts`, `pass_score`, `due_at`, `time_limit`. Ловится тестом
    `tests/integration/schema-parity.spec.ts`.
12. **Пять статусов прохождения**, не четыре: `not_assigned` ≠ `not_started`.
13. **Перечисления не выдумывать** — они перечислены в `docs/02-data-model.md`
    («Перечисления, снятые с эталона»). Новое значение — через обсуждение, не молча.
14. **Все журналы пишут `request_context`** (ip, geo, user_agent) одинаково.
15. **Чужой тенант — 404, не 403.** Это касается файлов, отчётов и страниц.

## Команды
```
pnpm dev:up        # поднять postgres+minio, накатить миграции, засеять данные
pnpm dev           # запустить приложение
pnpm db:generate   # сгенерировать миграцию из схемы
pnpm db:migrate    # применить миграции
pnpm test          # unit + integration
pnpm test:e2e      # playwright
pnpm lint && pnpm typecheck
```

## Экономия контекста
Основная сессия — диспетчер: читает память и `docs/32` §Б, ставит задачи, мержит PR.
Каждый PR делает субагент — модель по типу задачи, не по умолчанию:

| Тип задачи | Модель | Пример |
| --- | --- | --- |
| Схема, миграции | Opus | новая таблица, RLS-политика, `drizzle-kit generate` |
| Сервис с бизнес-логикой | Opus | подсчёт прогресса, правила прохождения, `server/services/*` |
| Многомодульная спека, стык нескольких модулей | Opus | назначения ↔ траектории ↔ уведомления |
| Разбор противоречий ТЗ | Opus | докерасхождение с эталоном, решение без заказчика |
| Правки docs, i18n, скрипты, CI | Sonnet | `docs/*.md`, `i18n/*.json`, `.github/workflows/*` |
| Вёрстка по готовому мокапу, переименования | Sonnet | компонент один в один с `docs/mockups/*.html` |
| Тесты по готовому образцу | Sonnet | спека по аналогии с существующей |

Перед пушем — один полный прогон `pnpm check` (lint → typecheck → `test:quiet` → `e2e:quiet`).
Не гонять тесты по нескольку раз «на всякий случай»; отдельным файлом — только пока чинишь
конкретное падение. Вывод команд смотреть через `grep`/`tail`/`head`, не выводить целиком.
Один скриншот на PR (финальный экран); мокапы читать текстом (`docs/mockups/*.html` через
`grep`/`sed`), а не картинками.

Перед созданием PR всегда `git fetch && git rebase origin/main` — ветка, созданная до
squash-merge предыдущей, даёт `CONFLICTING`, и CI на PR не запускается. После зелёного CI —
squash-merge самому, затем обновить стенд (`scripts/deploy-demo.sh` или авто из CI) и прислать
ссылку.

Визуальные тесты по мокапам — отдельный PR (`visual-mockups`), не смешивать с функциональными.

## Definition of Done
Lint, typecheck и тесты зелёные · покрытие нового сервиса ≥ 80% · миграция при изменении схемы ·
экран работает на 320px и с клавиатуры · ошибки объясняют, что делать · обновлены `docs/` ·
действия, меняющие чужие данные, пишутся в `audit_log`.

## Что читать перед типовыми задачами

| Задача | Читать |
| --- | --- |
| Назначение, его параметры или аудитория | `docs/15-assignments.md` §14 целиком |
| Тест, вопрос, попытка | `docs/12-tests-questions.md` §14 |
| Траектория | `docs/17-programs-trajectories.md` §14.3 (язык полотна) |
| Отчёт или журнал | `docs/22-reports.md` §13 (единый каркас колонок) |
| Уведомление | `docs/23-notifications.md` §13 |
| Экран | `docs/05-screens.md` §5.14 |
| Любая таблица | `docs/02-data-model.md`, включая раздел перечислений |

## Чего не делать
- Не добавлять зависимости без причины в PR.
- Не выдумывать поля и правила: если ТЗ молчит — задать вопрос, а не угадать.
- Не копировать код и вёрстку LMS Collaborator: эталон — только источник требований.
- Не отключать RLS «на время отладки».

Инварианты пакета, дополняющие список выше:
16. **Поведение этапа — через флаги возможностей, а не по коду этапа.** Проверка вида
    `if (stage.code === 'knowledge')` запрещена, всё идёт через `stageCan()`.
17. **Кандидат и сотрудник — одна запись `users` с разным `kind`.** Ни одна выборка людей
    не выполняется без явного фильтра по `kind`.
18. **ИИ не принимает решений о людях.** Автоматического отказа кандидату нет ни при каком
    результате; оценка модели — вход для человека.
19. **Перечень `media_assets.origin` меняется только через `docs/v2/40` §4**, одной
    миграцией, и никогда `drop constraint` из модульного документа.
