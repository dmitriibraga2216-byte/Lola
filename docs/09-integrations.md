# Lola LMS — ТЗ. Часть 9. Внешние интеграции и подключение по OAuth

Раздел написан на опыте интеграции Google в Loopa: там эти грабли уже собраны, и повторять
их в Lola не нужно. Механика ниже — обязательная для любой интеграции, где тенант
подключает свой аккаунт во внешнем сервисе (Google, Microsoft, Zoom, календарь, диск).

## 9.1 Какие интеграции нужны

| Интеграция | Зачем в Lola | Этап |
| --- | --- | --- |
| Telegram Bot | уведомления, привязка chat_id, автологин по ссылке | R1 |
| SMS-провайдер | OTP и критичные уведомления | R1 |
| SMTP / почтовый провайдер | письма руководителям, отчёты | R1 |
| S3 | медиа уроков | R1 |
| Вебхуки наружу | события обучения в чужие системы | R1 |
| API-токены | интеграция с учётной системой тенанта (люди, оргструктура) | R1 |
| Google OAuth | вход через Google, импорт людей из Workspace, календарь очных занятий, видео с Диска | R2 |
| Zoom / Google Meet | вебинары | R2 |

## 9.2 Подключение по OAuth — обязательная механика

Шесть шагов, все реализуются одинаково для любого провайдера:

1. `GET /integrations/:provider/status` — `is_configured()`: есть ли ключи приложения
   (client_id/secret) и подключён ли аккаунт тенанта. Две разные вещи, два разных ответа.
2. Кнопка «Підключити» в интерфейсе просит у сервера ссылку — клиент **не собирает** URL сам.
3. `GET /integrations/:provider/auth-url` собирает ссылку и кладёт в неё `state`.
4. Провайдер возвращает пользователя на `GET /integrations/:provider/callback`.
5. Окно авторизации закрывается само.
6. Панель перечитывает состояние и показывает результат.

### Правила, на которых обычно спотыкаются

- **`access_type=offline` и `prompt=consent` — обязательны оба.** Без первого приходит только
  короткий токен, и ночная фоновая задача наутро мертва. Без второго при повторном подключении
  провайдер считает, что согласие уже дано, `refresh_token` не присылает — и кнопка
  «підключити заново» тихо ничего не обновляет.
- **Тенант берётся из `state`, а не из сессии.** Колбек прилетает в отдельном окне, на cookie
  полагаться нельзя. `state` — одноразовый: использован → удалён.
- **`state` хранится в БД, а не в памяти процесса.** Словарь в памяти переживает ровно до
  рестарта и ломается на втором воркере: «Вхід не завершено: немає коду». Таблица
  `oauth_states(id, tenant_id, provider, state_hash, created_by, expires_at, consumed_at)`,
  срок жизни 10 минут.
- **`access_token` не хранится вообще.** Храним только `refresh_token`, короткий токен
  запрашиваем каждый раз заново.
- **`refresh_token` шифруется.** AES-GCM, ключ из окружения, в БД — только шифротекст.
  Хранение секрета в открытом `text` — это дефект, а не «пока так».
- **Панель следит за окном, а не только за `postMessage`.** Окно могли закрыть крестиком —
  сообщения не будет, а состояние перечитать всё равно надо.
- **Регистр и имя ключа проверяются тестом.** Реальный случай: писали `GOOGLE_REFRESH_TOKEN`,
  читали `google_refresh_token` — панель показывала «подключено», интеграция молчала.
  Имена ключей — константы в одном модуле, тест round-trip: записали → прочитали → совпало.

### Что обязано быть сразу, а не «потом»

- `POST /integrations/:provider/disconnect` — отключение из интерфейса, а не руками в базе.
- Проверка готовности аккаунта на стороне провайдера (например, подтверждена ли локация,
  выданы ли нужные права) **до** первой рабочей операции, с понятным текстом ошибки.
- Журнал: подключение, отключение, обновление токена, отказ провайдера — в `audit_log`.

## 9.3 Состояния, которые показывает интерфейс

Приоритет важен: ошибка перебивает норму, «не подключено» показывается раньше «работает».

| Состояние | Когда | Что видит человек |
| --- | --- | --- |
| Не налаштовано | нет ключей приложения | «Інтеграцію не налаштовано. Зверніться до адміністратора Lola» |
| Не підключено | ключи есть, аккаунта нет | «Підключіть акаунт» + кнопка |
| Підключається | идёт авторизация | спиннер в кнопке, окно открыто |
| Помилка підключення | колбек вернул ошибку или `state` протух | текст ошибки + «Спробувати ще раз» |
| Мовчить | токен есть, но последние N операций упали | «Інтеграція не відповідає з 14:20» — перебивает «Працює» |
| Працює | всё хорошо | «Підключено як user@company.com, оновлено 5 хв тому» |

Два разных текста для «нет ключей» и «не подключено» — обязательное требование: чинят их
разные люди (мы и тенант).

## 9.4 Хранение секретов тенанта

```sql
create table tenant_secrets (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null,
  provider text not null,              -- google | zoom | sms | smtp | s3
  key text not null,                   -- константа из модуля ключей
  value_encrypted bytea not null,      -- AES-GCM
  nonce bytea not null,
  account_label text,                  -- user@company.com — для интерфейса
  status text not null default 'active', -- active | revoked | failing
  last_ok_at timestamptz,
  last_error text,
  created_by uuid references users(id),
  unique (tenant_id, provider, key)
);
```

Правила: значение никогда не возвращается наружу (ни в API, ни в логах) — только
`account_label` и статус; ротация ключа шифрования предусмотрена миграцией
(перешифрование пачкой в фоновой задаче).

## 9.5 Вебхуки наружу

События: `enrollment.completed`, `attempt.passed`, `attempt.failed`, `certificate.issued`,
`assignment.overdue`, `user.created`. Подпись `X-Lola-Signature` (HMAC-SHA256 по телу),
три повтора с экспонентой, журнал доставок с телом запроса и ответом, ручной повтор из UI.

## 9.6 Входящий API для учётной системы тенанта

- Токен тенанта со скоупами, показывается один раз при создании.
- `POST /api/v1/sync/people` — идемпотентная синхронизация по `external_id`:
  создаёт, обновляет, архивирует отсутствующих (флагом).
- `POST /api/v1/sync/org` — подразделения и точки.
- Лимит 60 запросов в минуту на токен; при 429 — `Retry-After`.
- Каждая синхронизация пишет протокол, как импорт из файла: создано, обновлено, ошибки.
