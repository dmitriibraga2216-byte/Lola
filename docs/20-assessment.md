# Lola LMS — ТЗ. Часть 20. Оцінка персоналу та чек-листи

## 1. Назначение и границы

Модуль про оценку человека другими людьми, а не тестом. Два инструмента:

**Процедура оценки** — цикл, где человека оценивают по критериям он сам, руководитель и
коллеги (360°). Даёт срез компетенций, входит в ИПР.

**Чек-лист наблюдения** — наблюдатель проходит по пунктам прямо на смене, отмечает
выполнение, прикладывает фото. Это и аудит стандарта, и материал для обучения.
Для Каппі сюда же ложится программа тайного покупателя — та же механика, другой наблюдатель.

Входит: циклы оценки, анкеты, критерии и шкалы, назначение оценщиков, заполнение,
чек-листы, прохождение чек-листа на телефоне, отчёты, влияние на компетенции.
Не входит: аттестация знаний (`14`), ИПР и компетенции (`19`).

## 3. Сущности и поля

### 3.1 `rating_scales` — шкалы оценивания

| Поле | Тип | Комментарий |
| --- | --- | --- |
| `name` | text | «Зараховано / Не зараховано», «1–5», «Відсотки» |
| `kind` | text | `binary` \| `ordinal` \| `percent` \| `letters` |
| `options` | jsonb | `[{value:1, label:"Не відповідає", color:"coral"}, …]` |
| `pass_threshold` | numeric | с какого значения считается «норма» |
| `allow_na` | boolean | можно ли «не застосовно» |

### 3.2 `criteria_groups` и `criteria`

`criteria_groups`: `name`, `description`, `sort`, `weight`.
`criteria`: `group_id`, `text` (что оцениваем), `description` (как понимать),
`scale_id`, `weight`, `is_critical`, `requires_comment_below` (порог, ниже которого
комментарий обязателен), `competency_id` (связь с компетенцией), `requires_photo`.

### 3.3 `assessment_cycles` — процедура оценки

| Поле | Тип | Обяз. | Комментарий |
| --- | --- | :-: | --- |
| `title` | text | ✓ | «Оцінка бариста, 4 квартал» |

| `starts_at`, `ends_at` | timestamptz | ✓ | окно заполнения |
| `subjects` | jsonb | ✓ | кого оцениваем (та же адресация, что в `15`) |
| `rater_kinds` | text[] | ✓ | `self` \| `manager` \| `peer` \| `subordinate` \| `mentor` |
| `peers_count` | int | — | сколько коллег назначить автоматически |
| `peers_selection` | text | — | `auto` \| `by_subject` \| `by_manager` |

### 3.4 `assessment_tasks` и `assessment_answers`

`assessment_tasks`: `cycle_id`, `subject_user_id`, `rater_user_id`, `rater_kind`,

`due_at`, `submitted_at`, `decline_reason`.

| `critical_fail_rule` | text | `any_critical_fails_all` \| `none` |

## 4. Состояния

**Цикл:** `draft → active → calibration → finished`, ветка `cancelled`.
**Задача оценщика:** `pending → in_progress → submitted`, ветки `declined`, `expired`.
**Прогон чек-листа:** `draft → finished`; пункты плана действий живут своим циклом
`open → done | overdue`.

## 5. Экраны

### 5.1 Мої оцінки (сотрудник)

Вкладки: «Мене оцінюють» (сколько задач на меня, когда будут результаты),
«Я оцінюю» (список задач с дедлайном), «Результати» (по завершённым циклам).

Экран результата: лепестковая диаграмма по группам критериев — самооценка против оценки
руководителя и средней по коллегам; где расхождение больше 1 уровня — подсветка;
комментарии показываются только если оценщиков не меньше `min_raters_to_show`.

### 5.2 Заполнение анкеты

Один критерий — одна строка: текст критерия, подсказка «как понимать», шкала кнопками,
поле комментария (обязательное, если оценка ниже `requires_comment_below`).
Прогресс «12 з 28», автосохранение, кнопка «Надіслати».
Перед отправкой — сводка: средние по группам и предупреждение «Коментарі побачить
{кто именно}».

### 5.3 Управление циклом

Шаги настройки: анкета → кого оцениваем → кто оценивает → сроки → анонимность.
Мониторинг: сколько задач, сколько заполнено, кто не заполнил, кнопка «Нагадати».
Калибровка: руководители видят распределение оценок по своим людям и могут скорректировать
с обязательным комментарием (журналируется).

### 5.4 Чек-лист на телефоне (наблюдатель)

Экран прохождения: пункты списком по группам, у каждого — переключатель шкалы,
кнопка «Фото» (обязательна там, где `requires_photo`), поле комментария.
Внизу липко: «Виконано 14 з 20», кнопка «Завершити».
После завершения: процент, список провалов, форма плана действий — что исправить,
кто ответственный, до когда; кнопка «Надіслати керівнику».

Офлайн-режим обязателен: на кухне связь плохая, прогон должен заполняться без сети
и отправляться при появлении связи.

### 5.5 Результаты чек-листов

Таблица прогонов: дата, точка, наблюдатель, тип, процент, критические провалы, план действий.
Сводка по точкам: динамика процента по неделям, топ проваливаемых пунктов.
Карточка прогона: все ответы, фото, план действий со статусами.

порог показа комментариев, самооценка первой.

## 7. Правила и алгоритмы

1. **Назначение оценщиков.** `self` — сам человек; `manager` — руководитель точки и
   функциональные руководители; `peer` — коллеги той же точки и позиции, выбираются
   случайно в количестве `peers_count`, исключая тех, кто уже оценивает больше 5 человек.
2. **Анонимность.** При `anonymous_for_subject=true` человек видит только средние и
   комментарии без авторов; если оценщиков меньше `min_raters_to_show`, блок коллег
   не показывается вовсе — иначе автор вычисляется.
3. **Подсчёт.** По группе: `Σ(оценка × вес) / Σ(вес)`; по анкете — среднее по группам
   с их весами. Значения `n/a` исключаются из знаменателя.
4. **Критический пункт чек-листа** при `critical_fail_rule=any_critical_fails_all`
   обнуляет результат прогона независимо от остальных пунктов.
5. **План действий** обязателен, если прогон не пройден: нельзя отправить без хотя бы
   одного пункта с ответственным и сроком.
6. **Связь с компетенциями.** Критерий с `competency_id` создаёт оценку компетенции
   `source=assessment` с уровнем по маппингу шкалы (`19` §3.3).
7. **Частота.** Если чек-лист не проводился положенное число раз за период, руководителю
   уходит напоминание, а точка попадает в отчёт «Не перевірялись».
8. **Тайный покупатель** — тот же чек-лист с `kind=mystery`: наблюдатель не из штата,
   доступ по одноразовой ссылке без полноценного входа `[решение]`, результат виден
   только руководителю сети до момента публикации.
9. **Калибровка**: руководители видят распределение своих оценок против сети;
   корректировка возможна только с комментарием и фиксируется в журнале.

## 8. Уведомления

`assessment_task_assigned`, `assessment_due_soon`, `assessment_not_submitted`
(руководителю), `assessment_cycle_finished`, `assessment_results_ready`,
`checklist_due` (по частоте), `checklist_failed` (руководителю точки сразу),
`checklist_critical_failed` (руководителю сети), `action_item_due`, `action_item_overdue`.

## 9. Отчёты

**Результати оцінки**: по человеку, по точке, по компетенциям; расхождение самооценки
и оценки руководителя.
**Чек-листи**: динамика по точкам, топ проваливаемых пунктов, выполнение планов действий.
**Дисципліна перевірок**: кто из руководителей проводит чек-листы по норме, кто нет.
**Тайный покупатель**: волны, оценки, динамика, сравнение точек.

## 12. Крайние случаи

- Оценщик уволился в середине цикла → задача `expired`, средние считаются по оставшимся,
  если их не меньше порога.
- Коллега отказался оценивать («Не працював з цією людиною») → задача `declined`,
  автоматически назначается следующий кандидат.
- Чек-лист заполнялся офлайн, точка потеряла связь на час → данные хранятся локально,
  отправляются при появлении сети, дата прогона — фактическая, а не отправки.
- Фото обязательно, но камера недоступна → пункт нельзя отметить, подсказка объясняет.
- Два наблюдателя одновременно проходят один чек-лист на одной точке → допустимо,
  это два прогона; в отчёте видно оба.
- Человек оценивает сам себя строже руководителя → расхождение подсвечивается,
  это материал для разговора, а не ошибка.

## 13. Критерии приёмки

1. **Дано** цикл с `min_raters_to_show=3` и двумя коллегами-оценщиками,
   **тоді** блок коллег человеку не показывается.
2. **Дано** критерий с `requires_comment_below=3`, **коли** оценщик ставит 2 без комментария,
   **тоді** отправка заблокирована с подсказкой.
3. **Дано** чек-лист с критическим пунктом и правилом `any_critical_fails_all`,
   **коли** критический пункт провален, **тоді** результат прогона — «не пройдено»
   независимо от остальных 19 пунктов.
4. **Дано** прогон не пройден, **коли** наблюдатель пытается завершить без плана действий,
   **тоді** отказ с подсказкой.
5. **Дано** чек-лист заполнен офлайн, **коли** появилась связь, **тоді** прогон отправлен
   с фактическим временем заполнения, фото догрузились.
6. **Дано** критерий связан с компетенцией, **коли** цикл завершён, **тоді** у человека
   появилась оценка компетенции с источником `assessment`.

### 14.3 Чек-лист

`/checklists/:id/edit`: «Назва*», «Опис», «Шкала оцінювання*»,
«Додаткові опції»: «Дозволити пропускати питання», «Дозволити коментування кожного критерію»
(+ «Зробити поле обов'язковим»), «Інструкція для тих, хто відповідає на анкету»,
«Прикріплені файли», «Мітки», «Опублікувати», «Зображення для картки завдання».
Состав: та же библиотека критериев, таблица **«критерій - індикатор | Вага | Дії»**.

Разница между чек-листом и оценкой ровно одна и существенная: **у чек-листа «Вага»,
у оценки «Норма»**. Чек-лист считает набранную долю от суммы весов; оценка сравнивает
выставленный балл с нормой по каждому критерию. Фото и план действий в форме не предусмотрены.

### 14.4 Заморозка параметров после старта

Обе формы показывают предупреждение, когда заполнение уже началось:

> «Заповнення чек-листу вже почалось. Тепер заборонено змінювати частину параметрів.»
> «Вже почалося заповнення опитування. Тепер частину параметрів змінювати заборонено.»

Принимаем это правило дословно в `20` §7: после первого заполнения шкала, состав критериев,
веса и нормы становятся недоступны для правки; меняются только название, описание,
инструкция и метки. Остальное — только новой версией анкеты.

**Вывод для Lola `[решение]`.** Фотофиксация пункта, план действий по итогам и анонимность
с порогом показа — наше добавление (`20` §3.3, §6). В эталоне их нет. Фото оставляем:
без него оценка точки «по чистоте витрины» ничем не подтверждена.

Анонимность и конфиденциальность в эталоне — **два разных переключателя**:
«Конфіденційно» прячет ответы от всех, кроме владельца; «Анонімне» отрезает автора
от ответа вовсе. В `20` §6 принимаем оба, не смешивая.

«Опитування з умовами» — ветвление: следующий вопрос зависит от ответа на предыдущий.
Порог показа результатов (`20` §6.4) в эталоне отсутствует — наше добавление `[решение]`.

### 14.6 Словарь: критерий, группа, шкала

| Сущность | Экран | Поля |
| --- | --- | --- |
| Группа критериев | `/competence-dictionary/criteria-groups/create` | «Назва*», «Опис» (wysiwyg), «Мітки» |
| Критерий | `…/criteria-groups/:id/criteria/:id/edit` | «Назва*», «Опис» — и всё |
| Шкала | `/competence-dictionary/evaluation-scale/:id/edit` | «Назва*», «Опис», таблица **«Назва \| Числове значення \| Дії»**, кнопка «Додати варіант» |

Список групп показывает Назва · **Критерії** (все пункты списком прямо в ячейке) ·
Мітки · Дата створення.

**Шкала — это именованные уровни с числовым значением**, а не диапазон. Из живой установки:
«Оценка 1-5», «ТАК нІ», «100-95/5», «100/5», «Шкала оцінювання від 0 до 10»,
«Шкала ТАК-НІ», «ЧЛ КУхня» и «Шкала згоди (5 рівнів)» с описанием
«1 - Категорично не згоден, 2 - Швидше не згоден, 3 - Не знаю, 4 - Швидше згоден,
5 - Повністю згоден».

Две вещи, которые из этого следуют:

1. **Шкала — общий механизм, а не часть оценки.** Её же выбирают в параметрах назначения
   («Перетворити результат за шкалою», `15` §14.3), то есть процент теста переводится
   в ту же «1–5», что и оценка по критериям. В `02` шкала — самостоятельная таблица
   `evaluation_scales` + `evaluation_scale_levels(label, value)`, на неё ссылаются
   и анкеты, и назначения.
2. **Критерий не связан с компетенцией напрямую.** В эталоне у критерия только название
   и описание; связь с компетенцией — через группу и метки. Связь «критерий → компетенция»
   в `20` §3.1 остаётся `[решение]`: без неё результат оценки не ложится в профиль должности,
   а это половина смысла аттестации.

### 14.7 Редактор вопросов опроса

`/polls/:id/edit-v3`. Две вкладки, как у теста: «Питання» и «Опис та налаштування»;
в шапке виден режим («Лінійне опитування»), справа — навигатор «Створені питання»
с нумерованным списком.

**Четыре типа вопроса** (не семь, как в тесте):

**«Одиночне» · «Множинне» · «Вільна відповідь» · «По шкалі»**

У вопроса с вариантами: список ответов, «Додати варіант» и отдельно
**«або Свій варіант відповіді»** — поле «другое», которое респондент вписывает сам.
У свободного ответа — переключатель **«Дозволити прикріпляти файли до відповіді»**.

Ни баллов, ни правильных ответов у вопроса опроса нет — и это единственное, чем
редактор опроса отличается от редактора теста. В `02` это одна таблица вопросов
с `kind` и признаком `is_scored`, а не две.

## 15. Гипотезы и принятые по ним решения

### Г-20.1 Шаги «Завдання» и «Призначення» мастера оценки

**Снято частично.** Мастер создания оценки имеет четыре шага
(«Опис → Параметри → Завдання → Призначення»), но в режиме редактирования уже начатой
оценки доступны только первые два — третий и четвёртый не открываются.

**Гипотеза.** Шаг «Завдання» — это карточка назначения того же вида, что у остальных
типов (`15` §14.2), поскольку оценка назначается как `poll360`. Шаг «Призначення» —
выбор людей из фильтруемого списка. Кто кого оценивает (360°), задаётся, скорее всего,
через тип оценки: «за критеріями» — оценивает руководитель, «за компетенціями» —
оценивают несколько человек.

**Чем проверяется.** Создать черновик оценки и пройти мастер до третьего шага.

**Решение для Lola `[решение]`.** Роли оценщиков задаём явно, отдельной сущностью
`assessment_raters`, а не выводим из типа:

| Роль оценщика | Кто это | Вес по умолчанию |
| --- | --- | --- |
| `self` | сам человек | 0 (показывается, не считается) |
| `manager` | линейный руководитель | 2 |
| `functional_manager` | функциональный руководитель (`16` §14.2) | 1 |
| `peer` | коллега того же уровня | 1 |
| `subordinate` | подчинённый | 1 |
| `external` | наставник или тайный покупатель | 1 |

Состав оценщиков собирается автоматически из оргструктуры и правится руками.
Минимум по роли — параметр цикла: если подчинённых меньше трёх, их оценки
не показываются вовсе (см. Г-20.2).

### Г-20.2 Анонимность и порог показа

**Гипотеза.** У опроса эталона есть «Анонімне опитування» и «Конфіденційно» (`20` §14.5),
но у оценки этих переключателей в параметрах нет — там только правила комментирования.
Значит оценка по критериям в эталоне **не анонимна**: руководитель ставит балл от себя.

**Решение для Lola `[решение]`.** Анонимность — свойство **роли оценщика**, а не анкеты:

- `manager` и `self` — всегда именные. Руководитель отвечает за свою оценку.
- `peer`, `subordinate` — анонимные, с **порогом показа**: если по роли получено
  меньше `min_raters` ответов (по умолчанию 3), результаты этой роли не показываются
  никому, включая оцениваемого и его руководителя; в отчёте стоит
  «Недостатньо відповідей для показу».
- `external` — по настройке цикла.

Порог обязателен: при двух подчинённых анонимность фиктивна, и люди это понимают —
а значит пишут не то, что думают.

### Г-20.3 Колонки отчётов по оценке и чек-листам

**Гипотеза.** Отчёты `/assessment/report` и `/checklists/report` требуют выбора анкеты
и построены как остальные отчёты по предметам (`22` §13.3).

**Решение для Lola.** Специфичные колонки сверх постоянной левой части:

- **Оцінка**: Кого оцінюють · Роль оцінювача · Заповнено (так/ні) · Дата заповнення ·
  Середній бал · Бал по групах критеріїв · Розрив із нормою (по каждому критерию:
  факт минус норма, отрицательное — коралловым).
- **Чек-лист**: Об'єкт перевірки (точка, смена) · Хто перевіряв · Дата · Набрано балів ·
  Максимум · Відсоток · Кількість пропущених питань · Коментарі.

Отдельный разрез чек-листа `[решение]` — **по пунктам, а не по людям**: «какой пункт
чаще всего проваливают по всей сети». Это то, ради чего чек-лист и заводят:
не наказать смену, а увидеть, что витрину моют плохо везде.
