# Lola LMS — ТЗ. Часть 24. Налаштування простору, ролі, переклади, панель оператора платформи

## 1. Назначение и границы

Два уровня администрирования:

**Тенант** настраивает своё пространство: бренд, языки, модули, роли, политики, шаблоны,
интеграции, справочники.
**Оператор платформы** (мы) управляет тенантами: создание, тарифы, лимиты, метрики,
поддержка, вход «от имени», миграции.

Входит: настройки тенанта, редактор ролей, переводы интерфейса, политики, журнал,
панель оператора, тарифы и лимиты, impersonation, регистрация тенанта.
Не входит: интеграции (`09`), уведомления (`23`), справочники людей (`16`).

### 3.4.1 Политики эталона (сверено 19.09.2026, `/site/policies`)

Эталон группирует политики в десять разделов. Список приведён полностью — он определяет,
что в Lola должно быть настройкой, а не константой.

| Раздел | Настройки |
| --- | --- |
| **Аутентифікація** | «Ввімкнути авторизацію за допомогою тимчасового пароля»; «Приховати форму входу»; «Кількість спроб входу перед блокуванням» + «Встановити обмеження кількості спроб*» |
| **Ролі** | «Роль за замовчуванням*» (в снятой установке: Адміністратор Т.Т. / Адміністратор. / Користувач. / Тьютор.); «Не використовувати глобальні ролі»; «Режим призначення ролей»: «Зіставлення посад» \| «На основі даних імпорту» |
| **Підлеглі** | «Режим визначення підлеглих»: «Зіставлення посад» \| «На основі даних імпорту»; «Призначати підлеглими всіх користувачів у вкладених папках» |
| **Оргструктура** | «Режим»: «За групами користувачів» \| «На основі даних імпорту» \| «Гібридний (обидва режими)»; «Дозволити призначення користувача в кілька підрозділів оргструктури» (доступно только в режимах «На основі даних імпорту» и «Гібридний»); «Дозволити імпорт декількох оргструктур» |
| **Паролі** | «Відключити можливість відновлення пароля»; «Дозволити відновлення за номером телефону»; «Обмежити максимальний термін дії пароля»; «Мінімальна довжина пароля» + «Встановити довжину пароля*»; «Заборонити слабкі паролі»; «Змінити пароль після першого входу» |
| **Телефони** | «Дозволені телефонні коди країн» (в снятой установке — Ukraine) |
| **Сповіщення** | «Домени віртуальної пошти» + «Додати домен» — «Система буде ігнорувати всі листи, які закінчуються зазначеними доменами» |
| **Завдання** | «Дозволити користувачам призначати собі набори завдань у планах розвитку»; «Показати користувачеві завдання, які було переміщено до архіву» |
| **Користувачі** | «Показувати в звітах заблокованих користувачів»; «Не перезаписувати під час імпорту» (с выбором полей, напр. «Мітки») |
| **Захист даних** | «Вимкнути друк у ресурсах»; «Вимкнути копіювання вмісту контенту» |

Шапка экрана: «Відхилити зміни» и «Зберегти» — настройки копятся и сохраняются пачкой,
а не по одной. То же поведение принимаем в Lola.

**Что берём дословно.** Разделы «Оргструктура», «Підлеглі», «Захист даних»,
«Домени віртуальної пошти» и «Не перезаписувати під час імпорту» — в `24` §3.4 их не было;
добавляем. Особенно важны два:

1. **«Домени віртуальної пошти»** — у линейного персонала часто заводят технические адреса
   вида `ivan@local`; система должна молча не слать на них почту, а не копить ошибки.
2. **«Не перезаписувати під час імпорту»** с выбором полей — защита ручных правок от
   ночной синхронизации: метки, проставленные руками, импорт не затирает.

**Чего в эталоне нет, а у нас есть `[решение]`:** длина сессии, одновременные сессии,
параметры OTP (длина, срок, попытки, лимит отправок), автовыход по неактивности,
разрешённые страны входа, двухфакторность для админов. Эталон живёт на паре
«логин + пароль», Lola — на телефоне и одноразовом коде, поэтому её политики богаче
именно в этом месте.

### 3.5 Ролі

Список системных и своих ролей. Редактор: название, код, описание, набор скоупов
(чекбоксы по группам с поиском), область по умолчанию.
Кнопка **«Переглянути систему як роль»** — администратор видит интерфейс глазами роли,
не меняя свои права; режим помечен плашкой, выход в один клик.
Защиты: нельзя удалить роль, назначенную людям (сначала переназначить);
нельзя снять `settings.tenant` у последней роли с этим скоупом.

### 3.6 Переклади

Таблица ключей интерфейса: ключ, стандартный текст, свой текст, язык, кто менял.
Поиск по тексту, фильтр «только изменённые». Переопределение действует в пределах тенанта.
Кнопка «Повернути стандартний» на каждой строке и на всём наборе.
Экспорт и импорт в json — чтобы перевести целиком и залить.

### 3.7 Довідники і мітки

Города, подразделения, точки, должности, уровни должностей, метки, категории контента,
шкалы оценивания, группы критериев, шаблоны сертификатов — точки входа в редакторы
из `16`, `14`, `20`.

## 4. Панель оператора платформы

### 4.1 Список тенантов

Колонки: название, slug, план, статус, активных людей за 30 дней, объём медиа, дата создания,
окончание триала, последняя активность, версия схемы.
Фильтры: план, статус, активность, просроченная оплата.
Действия: открыть карточку, войти «от имени», приостановить, продлить триал, сменить план.

### 4.2 Карточка тенанта

Сводка: люди, курсы, назначения, попытки за месяц, объём хранилища, число SMS,
ошибки задач. Вкладки: настройки, лимиты, журнал действий, биллинг `[R2]`, заметки поддержки.

### 4.3 Создание тенанта

| Поле | Обяз. | Комментарий |
| --- | :-: | --- |
| Название | ✓ | |
| Slug | ✓ | уникален, `^[a-z0-9-]{3,30}$` |
| План | ✓ | trial / point / network / custom |
| Язык и таймзона | ✓ | |
| Телефон администратора | ✓ | ему уйдёт приглашение |
| ФИО администратора | ✓ | |
| Включённые модули | — | по плану, можно переопределить |
| Демо-контент | — | залить примеры курсов для знакомства |

После создания: тенант, системные роли, одна точка «Головна», позиция «Співробітник»,
администратор со всеми скоупами, приглашение по SMS/Telegram.

### 4.4 Тарифы и лимиты

`plans`: `code`, `name`, `modules[]`, `limits jsonb` (люди, хранилище ГБ, SMS в месяц,
API-запросы в минуту, вебхуки), `price_per_active_user`, `min_users`, `is_public`.
`tenant_limits` — переопределение лимитов конкретному тенанту.

Поведение при превышении: мягкое — предупреждение администратору и оператору;
жёсткое (хранилище, SMS) — блокировка операции с понятным текстом, обучение не останавливается.

### 4.4.1 Как это выглядит в эталоне (сверено 19.09.2026, `/statistics`)

Экран «Статистика» показывает ровно то, что нужно оператору платформы, и ничего лишнего:

- «Статистика використання ресурсів збирається раз на добу в 00:00».
- «Тарифний план: Pro».
- «Ліміт активних облікових записів: 150» — использовано 117, заблокированных 375.
- «Використано дискового простору: 43.677 GB», «Максимально допустимий розмір: 200 GB».

Три вывода для Lola:

1. **Лимит считается по активным, а не по всем.** Заблокированных втрое больше, чем
   активных (375 против 117) — в общепите это норма, люди приходят и уходят. Значит
   `tenant_limits.users` проверяется по `users.status = 'active'`, а блокировка человека
   немедленно освобождает место. Это правило дописываем в `25` §10.
2. **Сбор раз в сутки, а не в реальном времени.** Дисковое место и активность считает
   ночная задача; мгновенная цифра не нужна и дорога. Заводим `usage.collect` в 00:00
   по таймзоне тенанта и показываем время последнего сбора рядом с цифрой.
3. Порядок величин для одной сети: ~120 активных, ~1100 ресурсов, 44 ГБ файлов при потолке
   200 ГБ. Это и есть ориентир для нагрузочного теста в `07`, а не абстрактные «10 000 юзеров».

### 4.5 Вход «от имени» (impersonation)

Обязательные условия: указана причина (10–500 знаков), действие пишется в журнал
безопасности тенанта и платформы, сессия ограничена 60 минутами, в интерфейсе постоянная
коралловая плашка «Ви увійшли як {ім'я}. Вихід», запрещены: изменение ролей, выгрузка
персональных данных, отправка уведомлений `[решение]`.

### 4.6 Метрики платформы

Активные тенанты, MAU/WAU по тенантам, завершённые курсы за период, объём хранилища,
ошибки задач, доставляемость уведомлений, p95 API, самые тяжёлые запросы.

## 5. Регистрация тенанта самостоятельно (R2)

Форма: название сети, телефон, имя, число сотрудников, город. После подтверждения кода —
создаётся тенант на триале 14 дней с демо-контентом, человек сразу попадает в мастер:
добавить точки → добавить людей (импорт или ссылка-приглашение) → назначить первый курс.
Триал заканчивается: данные сохраняются 90 дней, вход остаётся, назначения новые создать нельзя.

## 6. Формы и валидации (ключевые)

| Поле | Валидация | Ошибка (uk) |
| --- | --- | --- |
| Slug тенанта | `^[a-z0-9-]{3,30}$`, уникален | «Адреса зайнята або містить недопустимі символи» |
| Акцентный цвет | из палитры бренда | «Колір має відповідати бренд-буку» |

## 7. Правила и алгоритмы

1. **Изменение настроек** пишется в `audit_log` со старым и новым значением;
   критичные (политики, роли, модули) дополнительно — в журнал безопасности.
2. **Выключение модуля** не удаляет данные и не ломает историю: отчёты по нему остаются
   доступными администратору.
3. **Смена тарифа вниз** проверяет, не превышены ли новые лимиты; если да — показывает,
   что именно мешает, и не применяется.
4. **Переопределение перевода** хранится отдельно от стандартного словаря: обновление
   системы не затирает тексты тенанта.
5. **Удаление тенанта** — двухшаговое: приостановка (данные живы, вход закрыт) и через
   30 дней полное удаление с выгрузкой архива владельцу. Прямое удаление запрещено.
6. **Экспорт данных тенанта** (GDPR и переезд): выгрузка всех таблиц в json + медиа
   архивом; собирается фоновой задачей, ссылка живёт 72 часа.
7. **Версия схемы** видна в карточке тенанта: после миграции все тенанты должны быть
   на одной версии, расхождение — алерт.

## 11. Крайние случаи

- Администратор тенанта снял себе все права → защита: последний администратор
  не может лишиться `settings.tenant`.
- Тенант выключил модуль, в котором есть незавершённые назначения → предупреждение
  со списком, назначения остаются, но недоступны людям; при включении продолжаются.
- Оператор вошёл «от имени» и закрыл вкладку → сессия сама истекает через 60 минут.
- Два администратора правят настройки одновременно → оптимистическая блокировка
  по версии, второму показывается, что изменилось.
- Тенант попросил удалить данные → приостановка, выгрузка архива, удаление через 30 дней,
  всё в журнале.
- Slug меняется после запуска → старые ссылки перестают работать; форма предупреждает
  и предлагает оставить редирект на 90 дней `[решение]`.

## 12. Критерии приёмки

1. **Дано** оператор входит «от имени» без причины, **тоді** отказ; с причиной —
   вход, плашка в интерфейсе, запись в журналах платформы и тенанта, уведомление
   администратору тенанта.
2. **Дано** тариф с лимитом 100 человек, в тенанте 120, **коли** оператор пытается
   понизить тариф, **тоді** отказ с указанием, что мешает.
3. **Дано** администратор изменил перевод кнопки, **коли** вышло обновление системы,
   **тоді** его текст сохранился.
4. **Дано** выключен модуль «Практикуми», **тоді** пункт исчез из меню, API отвечает 403,
   отчёты по прошлым практикумам остались доступны администратору.
5. **Дано** триал заканчивается через 7 дней, **тоді** администратору ушло уведомление;
   после окончания вход работает, новые назначения создать нельзя.
6. **Дано** режим «Переглянути систему як роль employee», **тоді** администратор видит
   интерфейс сотрудника, но его собственные права не изменились.

### 3.7.1 Категории (сверено 19.09.2026)

Два независимых справочника категорий:

- **«Категорії ресурсів»** — `/resources/categories/manage`. Плоский список, редактируется
  на месте, кнопка «Додати нову категорію» добавляет строку «Нова категорія».
  В снятой установке: «Саморозвиток», «1.Інформація про компанію», «2.Торгові точки»,
  «3.Кухня», «4.Офіс», «5.Меню Bulochki)», «6.Бланки контролю», «7.Бібліотека»,
  «8.Робота з колаборатором».
- **«Категорії каталогу навчання»** — `/manage/tasks/categories/manage`.
  В снятой установке две: «Саморозвиток», «Приклади завдань».

Нумерация в названиях («1.», «2.») — обходной путь: порядка у категорий нет, и люди
задают его цифрами в тексте. В Lola у категории есть `sort_order` и перетаскивание,
цифры в названии не нужны.

Два разных справочника — не дублирование: категория ресурса упорядочивает базу знаний,
категория каталога — витрину самозаписи. Их аудитории и смысл разные, объединять не надо.

## 13. Гипотезы и принятые по ним решения

### Г-24.1 Списка прав у роли в интерфейсе нет

**Проверено (`01` §1.9.1).** Редактора роли у администратора тенанта нет: роли приходят
от поставщика, назначаются человеку чекбоксами, а политика задаёт только роль
по умолчанию и режим назначения.

**Гипотеза о правах.** Раз меню перестраивается под активную роль, права в эталоне —
это набор доступных разделов, а не операций: «Тьютор» видит очереди проверки,
«Адміністратор Т.Т.» — свою точку. Гранулярности уровня «может править курс,
но не может удалять» по интерфейсу не видно.

**Решение для Lola `[решение]`.** Права — скоупы вида `<объект>.<операция>`
(`course.edit`, `review.grade`, `people.import`, `settings.tenant`), роль — набор скоупов,
у назначения роли есть **область**: тенант, подразделение или точка. Экран редактора:
группы скоупов с поиском, переключатель «выбрать всё в группе», предпросмотр
«что увидит эта роль».

Защиты: нельзя удалить роль, выданную людям; нельзя снять `settings.tenant`
у последней роли, где он есть; нельзя выдать себе скоуп, которого у тебя нет.

Цена: один экран и таблица `role_scopes`. Взамен — сеть заводит «наставника своей точки»
сама, не заказывая роль у поставщика и не ожидая релиза.

### Г-24.2 Модулей «включить / выключить» в эталоне нет

**Гипотеза.** Разделы меню в эталоне присутствуют все, даже неиспользуемые
(вебинары, форум, wiki, рабочие задачи — везде нули). Значит состав модулей
определяется тарифом на стороне поставщика и правами, а самостоятельного
выключателя у тенанта нет.

**Решение для Lola `[решение]`.** Переключатели модулей на уровне тенанта делаем
(`24` §3.2). Причина видна на самом эталоне: у Каппі в меню висят семь разделов,
которыми никто не пользуется, и каждый из них — это лишний пункт, в который
сотрудник заходит один раз, не находит ничего и запоминает, что система пустая.

Правило выключения: пункт исчезает из меню, API отвечает 403 с понятным кодом,
**ранее накопленные данные остаются доступны администратору** через отчёты —
выключение модуля не должно выглядеть как потеря данных.

### Г-24.3 Администратор тенанта и оператор платформы

**Гипотеза.** Снятая установка — инсталляция на одного клиента, и разделения нет:
«Адміністратор» видит и политики, и интеграции, и статистику потребления,
и шаблоны уведомлений. Тариф («Pro») показан, но не редактируется — значит
уровень платформы существует, просто живёт вне этого интерфейса.

**Решение для Lola.** Разделение обязательно (это SaaS, а не инсталляция):

- **Администратор тенанта** — всё внутри своего тенанта: люди, контент, назначения,
  политики, свои интеграции, свои шаблоны.
- **Оператор платформы** — список тенантов, тарифы и лимиты, вход «от имени»
  с причиной и ограничением по времени, метрики платформы, миграции.

Ни один экран оператора не доступен администратору тенанта, даже на чтение;
вход «от имени» виден администратору тенанта в его журнале безопасности —
клиент должен знать, что к нему заходили.

### Г-24.4 Три разных справочника шкал — и это правильно

**Проверено.** В эталоне три независимых реестра шкал:

| Реестр | Путь | Строка |
| --- | --- | --- |
| Шкали оцінки завдань | `/manage/tasks/evaluation-scales` | Назва · **Відображати у звітах** · **Характеристика оцінки** · **Діапазон оцінки завдання** |
| Шкали оцінювання (анкеты) | `/competence-dictionary/evaluation-scale` | Назва · **Числове значення** |
| Шкала компетенцій | `/competencies/scale` | Назва · Числове значення, плюс «Відображати результати оцінки як: Назва \| Числове значення» |

Разница содержательная, а не историческая. Первая переводит **диапазон процентов**
в название («85–100 → Відмінно»). Вторая и третья — это **перечень уровней**,
из которых оценщик выбирает.

**Решение для Lola.** Оставляем две сущности, не три:
`scales` с полем `kind` (`range` \| `levels`) и `scale_levels`
(`label`, `value`, `range_from`, `range_to`, `characteristic`, `show_in_reports`).
Шкала компетенций — это `levels` с флагом `display_as` (`label` \| `value`).
Слияния второй и третьей достаточно: разделять их незачем, обе выбирают уровень.
