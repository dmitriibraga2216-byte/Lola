# Lola LMS — ТЗ. Часть 25. Мультитенантність

Отдельный документ, потому что это не функция, а свойство всей системы: каждая строка,
каждый файл, каждая фоновая задача и каждый лог должны знать, чьи они. Ошибка здесь —
не баг интерфейса, а утечка данных одной сети в другую, после которой продукт продавать
нельзя.

## 1. Модель и выбор подхода

| Подход | Изоляция | Стоимость | Вердикт |
| --- | --- | --- | --- |
| Отдельная инсталляция на клиента (как в эталоне) | максимальная | высокая: каждое обновление × число клиентов | нет |
| База на тенанта в одном кластере | высокая | средняя: миграции × число баз, пул соединений | нет на старте, запасной путь для крупного клиента |
| **Схема на тенанта** | высокая | миграции по всем схемам, сложный поиск по всем | нет |
| **Общие таблицы + `tenant_id` + RLS** | высокая при дисциплине | низкая | **выбрано** |

Решение: **shared database, shared schema, row-level security**. Для клиента, который
потребует физического разделения (тендер, требование безопасности), предусмотрен путь
«вынести тенанта в отдельную базу» — см. §11.

## 2. Что такое тенант

Тенант — одна сеть-клиент. Внутри тенанта: подразделения, точки, должности, люди, контент,
назначения, отчёты, настройки, интеграции, файлы. Между тенантами не пересекается ничего,
кроме кода приложения и системных справочников платформы (планы, версии, шаблоны писем
платформы).

Один и тот же человек может работать в двух тенантах (например, франчайзи и управляющая
компания) — это **две разные записи `users`** с одним номером телефона и двумя профилями.
При входе по номеру, найденному в нескольких тенантах, показывается выбор пространства.

## 3. Изоляция данных

### 3.1 Правило схемы

Каждая доменная таблица содержит `tenant_id uuid not null` — включая таблицы-связки и
журналы. Исключения (таблицы платформы без `tenant_id`): `tenants`, `plans`, `migrations`,
`platform_admins`, `platform_audit`, `oauth_states` (там `tenant_id` nullable до выбора),
`otp_codes` (до выбора пространства).

### 3.2 RLS

```sql
alter table <t> enable row level security;
alter table <t> force row level security;        -- владелец таблицы тоже подчиняется

create policy tenant_isolation on <t>
  using      (tenant_id = current_setting('app.tenant_id', true)::uuid)
  with check (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

- `force row level security` обязателен: без него владелец таблицы обходит политику.
- `with check` обязателен: без него можно вставить строку с чужим `tenant_id`.
- Роль приложения: `create role app_user nologin nobypassrls;` — гранты только на нужные
  таблицы, без `superuser`, без `bypassrls`.
- Миграции применяются отдельной ролью `migrator`, которая не используется приложением.

### 3.3 Единственная точка доступа к БД

```ts
export async function withTenant<T>(
  tenantId: string, userId: string | null, fn: (tx: Tx) => Promise<T>
): Promise<T> {
  return db.transaction(async (tx) => {
    await tx.execute(sql`select set_config('app.tenant_id', ${tenantId}, true)`);
    await tx.execute(sql`select set_config('app.user_id', ${userId ?? ''}, true)`);
    return fn(tx);
  });
}
```

Правила:
- `set_config(..., true)` — локально для транзакции: значение не утекает в следующий запрос
  из пула соединений. Это главная ловушка пула — `set` без `local` остаётся на соединении.
- Прямой вызов драйвера в обход `withTenant()` запрещён; линтер-правило и code review.
- Тенант берётся **только** из сессии. Параметр `tenantId` в теле или query игнорируется
  всегда, даже у платформенного администратора (у него отдельный модуль, §7).

### 3.4 Тест полноты

`tests/integration/rls.spec.ts` перебирает `information_schema.tables`, находит все таблицы
с колонкой `tenant_id` и падает, если у таблицы:
- не включён RLS или не включён `force`;
- нет политики `tenant_isolation`;
- политика без `with check`.

Второй тест — фактическая изоляция: создаются два тенанта с данными, под каждым выполняется
`select count(*)` по каждой таблице, результат чужого тенанта обязан быть 0.

Третий — попытка вставки с чужим `tenant_id` внутри `withTenant` обязана падать.

## 4. Изоляция файлов

- Ключи в S3: `t/<tenant_id>/<yyyy>/<mm>/<uuid>.<ext>` — тенант в префиксе, а не в имени.
- Доступ только по подписанным ссылкам на 10 минут; публичных бакетов нет.
- Перед выдачей ссылки сервис проверяет, что `media_assets.tenant_id` совпадает с сессией.
- Публичные исключения: страница проверки сертификата (`/c/<token>`) и гостевой блок
  на странице входа — оба отдают только то, что явно помечено публичным.
- Квота хранилища считается по префиксу тенанта, ночной задачей.

## 5. Изоляция фоновых задач

Каждая задача несёт `tenant_id` в payload и выполняется внутри `withTenant()`.
Запрещено: задачи, которые «пробегают по всем тенантам» внутри одной транзакции.
Правильно: планировщик раскладывает работу на задачи по тенантам
(`due.scan` → N задач `due.scan:tenant`), каждая изолирована и падает отдельно.

Очередь общая, но с ключом справедливости: один тенант с 5000 уведомлений не должен
задерживать остальных — берём партиями по тенантам по кругу (round-robin) `[решение]`.

Список тенантов для круга берётся либо из платформенной таблицы `tenants` (все работающие),
либо из функции `SECURITY DEFINER`, которая отдаёт только идентификаторы тенантов с работой
(`tenants_with_queued_notifications()`, `tenants_with_active_attempts()`,
`tenants_with_pending_webhooks()`). Запрещено строить его запросом к таблице с `tenant_id`
через общее соединение вне `withTenant()`: без `app.tenant_id` политика RLS не пропускает ни
одной строки, запрос не падает, а возвращает пустой список — и круг не обслуживает никого.
Проверяется `tests/integration/job-tenant-sources.spec.ts` (источники под ролью `app_user`) и
сторожем `tests/unit/shared-db-guard.spec.ts` (общее соединение не касается таблиц с
`tenant_id`). `[добавлено 25.09.2026: так с 19.09 не работали notification.dispatch,
attempt.expire и webhook.deliver]`

## 6. Изоляция в приложении

| Слой | Что обязано |
| --- | --- |
| Сессия | хранит `tenant_id`; смена пространства = новая сессия |
| Кеш | ключи всегда с префиксом `t:<tenant_id>:` |
| Поиск | индексы с фильтром по тенанту; pgvector-запросы тоже под RLS |
| Логи | каждая строка содержит `tenant_id` и `trace_id` |
| Метрики | лейбл `tenant` на бизнес-метриках, без персональных данных |
| Вебхуки | подписываются секретом тенанта, URL из настроек тенанта |
| i18n | переопределения строк живут в тенанте |
| Файлы экспорта | попадают в хранилище тенанта, ссылка подписана |

## 7. Кросс-тенантные операции

Единственный модуль, который видит несколько тенантов — панель оператора платформы
(`24-settings-platform.md`). Правила:

1. Отдельная роль БД `platform_admin` с `bypassrls`, используемая только этим модулем.
2. Отдельный неймспейс API `/platform/*` с собственной проверкой прав.
3. Ни одна строка чужого тенанта не отдаётся в обычные эндпоинты, даже оператору.
4. Панель показывает **агрегаты** (сколько людей, курсов, задач), а не содержимое:
   чтобы увидеть данные, нужен вход «от имени» с причиной и уведомлением администратора.
5. Каждый запрос панели пишется в `platform_audit` (кто, что, по какому тенанту).
6. **Отдельный хост консоли** `[решение владельца продукта, 26.09.2026; реализовано ops-console-1]`.
   `OPS_HOST` (прод: `ops.lmscappi.pp.ua`) — на нём открыты только `/ops/*`, `/api/v1/platform/*` и
   служебное (сборка Nuxt, словари, health); тенантские страницы и API — `404`. На любом другом хосте
   `/ops/*` и `/api/v1/platform/*` — `404`. Проверка — в `01.host` раньше резолва тенанта
   (`server/services/opsHost.ts`), иначе `ops.<base>` приняли бы за тенанта `ops`; slug, совпадающий
   с поддоменом консоли, тенанту не выдаётся. Cookie оператора `lola_ops` — host-only (без `Domain`),
   `SameSite=Strict`, `Secure`; тенантская сессия и Bearer на хосте консоли не читаются. Вход
   «від імені» с хоста консоли — одноразовой ссылкой (60 с) на хост тенанта (`/impersonate/go`),
   токен сессии в ней зашифрован ключом приложения. Без `OPS_HOST` (dev, тесты) — консоль по пути
   `/ops` на общем хосте, как раньше.
7. **Роли операторов** `[решение владельца продукта, 26.09.2026; реализовано ops-console-1]`.
   Перечисление `platform_role` (docs/02): одна функция `platformCan(role, action)`
   (`shared/domain/platformRoles.ts`), её зовёт **каждая** ручка `/api/v1/platform/*` через
   `requirePlatform(event, action)` (отказ — `403 platform.forbidden`); консоль только прячет кнопки.
   Статический тест `tests/unit/platform-roles.spec.ts` валит CI на ручке без действия.

   | Действие | owner | admin | billing | support | viewer |
   | --- | :-: | :-: | :-: | :-: | :-: |
   | Чтение: компании, пользователи компании, метрики, тарифы, объявления, журнал, операторы | ✓ | ✓ | ✓ | ✓ | ✓ |
   | Чтение денег: лимиты, подписка, платежи (`billing.read`) | ✓ | ✓ | ✓ | — | ✓ |
   | Создать компанию, править (название, домен, SMTP TLS, этапы) | ✓ | ✓ | — | — | — |
   | Приостановить / возобновить | ✓ | ✓ | — | — | — |
   | Окончательное удаление (`purge`) и его отмена | ✓ | — | — | — | — |
   | Вход «від імені», сброс 2FA пользователю компании | ✓ | ✓ | — | ✓ | — |
   | Лимиты, платёж, смена тарифа, продление (в т. ч. `plan`/`trialEndsAt` в PATCH компании) | ✓ | ✓ | ✓ | — | — |
   | Объявления платформы | ✓ | ✓ | — | — | — |
   | Операторы: пригласить, сменить роль, деактивировать, сбросить 2FA оператору | ✓ | — | — | — | — |

   Действующие на момент миграции `0099` операторы получили `owner`, новый по умолчанию — `viewer`.
   Последнего активного `owner` нельзя понизить или деактивировать; свою роль менять нельзя.
8. **Второй фактор операторов обязателен** `[решение владельца продукта, 26.09.2026]`. Механизм — тот же,
   что у пользователей тенанта (docs/24 §3.4.2: `totp.ts`, секрет шифротекстом `crypto.ts`, резервные
   коды хешами argon2id, `last_used_step`), хранение — колонками `platform_admins` и таблицей
   `platform_admin_recovery_codes` (оператор вне тенантов). Любой вход по паролю даёт промежуточную
   сессию: открыты только `/platform/two-factor/*`, `me` и выход, остальное — `401 two_factor_required`.
   Нет фактора — экран подключения, есть — экран кода. Сбросить фактор другому оператору может только
   `owner`, с причиной; все сессии оператора при этом гаснут; запись — в `platform_audit`.

## 8. Жизненный цикл тенанта

| Этап | Что происходит |
| --- | --- |
| Создание | тенант, системные роли, первая точка, позиция, администратор, приглашение |
| Наполнение | импорт людей, контент, настройки, интеграции |
| Работа | обычная эксплуатация, лимиты по плану |
| Приостановка | вход закрыт, данные целы, фоновые задачи остановлены, уведомления не идут |
| Экспорт | архив данных и медиа по запросу владельца |
| Удаление | только после приостановки и явной команды оператора, через 30 дней, необратимо |

Мягкое удаление тенанта: `tenants.status='archived'` + `archived_at`. Задача `tenant.purge`
удаляет данные партиями по таблицам в порядке зависимостей и пишет отчёт.

## 9. Настройка и кастомизация тенанта

Что тенант может менять: название, логотип, акцент из палитры бренда, языки, часовой пояс,
тихие часы, набор модулей (в рамках плана), роли и скоупы, шаблоны уведомлений, переводы
строк, справочники, значения по умолчанию для обучения, интеграции.

Что не может: цвета ролей (солнце — действие, бирюза — результат, коралл — ошибка),
структуру данных, набор скоупов, механику попыток, правила RLS.

Домены: `app.lola.ua/<tenant-slug>` на R1; поддомен `<slug>.lola.ua` — R2;
собственный домен клиента (`navchannya.kappi.ua`) — R3, через CNAME и сертификат
Let's Encrypt по DNS-01.

## 10. Лимиты и справедливость ресурсов

**Сверено с эталоном 19.09.2026** (`/statistics`, см. `24` §4.4.1). Оттуда два правила,
которые в Lola действуют дословно:

1. **Лимит людей считается по активным.** В снятой установке при лимите 150 активных было
   117 активных и 375 заблокированных. Блокировка человека немедленно освобождает место,
   его история обучения сохраняется. Проверка лимита —
   `count(*) where tenant_id = ? and status = 'active'`, и она выполняется при активации,
   а не при каждом запросе.
2. **Потребление ресурсов собирается раз в сутки в 00:00**, не в реальном времени.
   Задача `usage.collect` считает дисковое место и активность по тенанту и пишет
   в `tenant_usage`; интерфейс показывает цифру вместе с временем сбора.
   Жёсткие лимиты (хранилище, SMS) при этом проверяются в момент операции по текущему
   значению, а не по ночному снимку — иначе тенант за день выйдет за потолок вдвое.

| Ресурс | Лимит по плану | Поведение при превышении |
| --- | --- | --- |
| Активных людей в месяц | 30 / 300 / без ограничения | мягкое: предупреждение, счёт по факту |
| Хранилище | 10 / 100 / 500 ГБ | жёсткое: загрузка новых файлов блокируется |
| SMS в месяц | 100 / 1000 / по договору | жёсткое: остаётся Telegram и in-app |
| API-запросы | 60 / 300 / 600 в минуту | 429 с `Retry-After` |
| Вебхуки | 1 / 10 / 50 endpoint | жёсткое |
| Размер выгрузки | 50 000 строк | фоновая задача, ссылка на файл |

Обучение никогда не останавливается лимитами: блокируются только загрузка файлов,
SMS и API — то, что стоит денег платформе.

## 11. Вынос тенанта в отдельную базу (запасной путь)

Если клиент требует физического разделения:
1. Создаётся отдельная база с той же схемой и той же версией миграций.
2. Данные тенанта выгружаются `pg_dump` с фильтром по `tenant_id` (готовый скрипт
   `scripts/extract-tenant.ts`, порядок таблиц по зависимостям).
3. Медиа копируются `mc mirror` по префиксу `t/<tenant_id>/`.
4. В роутере приложения тенант помечается `db_url_override` — соединение берётся из
   отдельного пула.
5. RLS остаётся включённым и там: код не меняется, потому что `withTenant()` тот же.

Требование к коду: **никаких прямых `join` между тенантами** — иначе этот путь закрывается.

## 12. Миграции и версии схемы

- Миграции применяются один раз для всех тенантов (общая схема) — это главный выигрыш
  выбранного подхода.
- Миграция обязана быть обратно совместимой: сначала добавляем колонку с дефолтом,
  потом переносим данные фоновой задачей по тенантам, потом переключаем код.
- Долгие переносы данных (`backfill`) — всегда задача по тенантам, а не один `update`
  на всю таблицу: иначе блокировка кладёт всех клиентов сразу.
- Версия схемы видна в карточке тенанта; расхождение версий — алерт оператору.

## 13. Безопасность и приватность

1. **Проверка на каждом слое**: RLS в базе, `withTenant` в сервисе, проверка скоупа
   в эндпоинте, фильтр в сериализаторе. Ни один слой не считается достаточным.
2. **Персональные данные** (телефон, дата рождения, комментарии) не попадают ни в логи,
   ни в метрики, ни в тексты ошибок.
3. **Экспорт данных тенанта** доступен только администратору тенанта и оператору
   с записью в оба журнала.
4. **Удаление данных человека** (GDPR) выполняется внутри тенанта и не затрагивает
   статистику курса: результаты остаются обезличенными.
5. **Секреты тенанта** (токены интеграций) шифруются AES-GCM, ключ в окружении,
   ротация — фоновой задачей (`09-integrations.md` §9.4).
6. **Резервные копии**: общий дамп базы содержит все тенанты, поэтому доступ к бэкапам —
   только у оператора; восстановление одного тенанта делается через `extract-tenant`.

## 14. Критерии приёмки (обязательны к автоматизации)

1. **Дано** две тенанта с данными, **коли** выполняется запрос под тенантом А по каждой
   таблице системы, **тоді** ни одна строка тенанта Б не возвращается.
2. **Дано** новая таблица с `tenant_id` без политики, **тоді** тест `rls.spec.ts` падает
   с именем таблицы.
3. **Дано** попытка вставки строки с чужим `tenant_id` внутри `withTenant`, **тоді** ошибка БД.
4. **Дано** запрос с параметром `tenantId` чужого тенанта в теле, **тоді** параметр
   игнорируется, данные — из сессии.
5. **Дано** соединение из пула, которое обслуживало тенанта А, **коли** следующий запрос
   пришёл от тенанта Б, **тоді** `current_setting('app.tenant_id')` равен Б
   (проверка отсутствия утечки `set` без `local`).
6. **Дано** файл тенанта А, **коли** пользователь тенанта Б запрашивает его по прямому ключу,
   **тоді** 404, а не 403 — существование чужого файла не подтверждается.
7. **Дано** фоновая задача упала на тенанте А, **тоді** задачи остальных тенантов выполнились.
8. **Дано** 5000 уведомлений у тенанта А и 5 у тенанта Б, **тоді** уведомления Б уходят
   в течение минуты, а не после очереди А.
9. **Дано** оператор открыл панель платформы, **тоді** он видит агрегаты и не видит
   ни одной персональной строки без входа «от имени».
10. **Дано** тенант приостановлен, **тоді** вход закрыт, фоновые задачи по нему не идут,
    уведомления не отправляются, данные целы.

## 15. Чек-лист для разработчика при добавлении сущности

- [ ] Колонка `tenant_id uuid not null` и внешний ключ на `tenants`.
- [ ] Индекс, начинающийся с `tenant_id`, под основные выборки.
- [ ] RLS: `enable`, `force`, политика с `using` и `with check`.
- [ ] Уникальные ограничения включают `tenant_id` (иначе слоган «уникально» станет
      глобальным: два тенанта не смогут иметь курс с одинаковым slug).
- [ ] Доступ только через `withTenant`.
- [ ] Файлы — с префиксом тенанта.
- [ ] Фоновые задачи получают `tenant_id` в payload.
- [ ] Записи в `audit_log` содержат `tenant_id`.
- [ ] Тест изоляции проходит.

## 16. Решения по открытым вопросам

### 16.1 Адресация тенанта: поддомен с первого дня

**Решение.** `<slug>.lola.app`, а не путь `/t/<slug>`.

Почему. Cookie сессии — `httpOnly; Secure; SameSite=Lax`, привязанная к хосту.
На путях все тенанты делят один origin: любая XSS в одном тенанте достаёт куку другого,
`localStorage` общий, а отзыв сессии одного тенанта задевает остальных.
Поддомен даёт границу происхождения бесплатно.

Цена: wildcard-сертификат (`*.lola.app`, Let's Encrypt через DNS-01) и wildcard-запись
в DNS — оба настраиваются один раз в `26`. Резолв тенанта — по `Host`, до всего
остального, в серверном middleware; неизвестный поддомен отдаёт 404, а не страницу входа,
чтобы перебором нельзя было узнать список клиентов.

Собственный домен клиента (`navchannya.cappi.ua` через CNAME) — R2,
модель та же, добавляется только проверка владения доменом.

**Сделано (докс/33 D-059).** Поле `tenants.custom_domain` (уникальное, nullable) задаётся
оператором в панели платформы (карточка тенанта → «Домен»). Резолв в `01.host` не меняется
по структуре: `decideHost` по-прежнему сначала проверяет `<slug>.<base>`, и только для хоста,
который под эту схему не подпадает (свій домен, localhost, IP, `TENANT_HOST_DEFAULT`),
`resolveTenantByHost` ищет точное совпадение с `custom_domain`, прежде чем откатиться на
тенант по умолчанию — «сперва свій домен, потім `<slug>.<base>`» из порядка проверок, а не
буквально первой веткой кода (поддомен своего тенанта и собственный домен не пересекаются
на практике). Google-вход (`GET /auth/google/url`) берёт тенант из `event.context.hostTenant`
(тот же `01.host`), а не из `?tenant=` — параметр остаётся фолбеком там, где резолв по хосту
выключен (`TENANT_HOST_BASE` не задан: dev, тесты). Проверка владения доменом (подтверждение
записи в DNS) не автоматизирована — оператор убеждается вручную перед тем, как вписать домен
в карточку (инструкция по CNAME и сертификату — `27`).

### 16.2 Данные и бэкапы: Украина по умолчанию

**Решение.** Основная база, хранилище и бэкапы — на территории Украины
(свой сервер в `26`, при переезде в облако — украинский или европейский регион
с явной записью в договоре). Требование «наши данные только в Украине» выполняется
по умолчанию, а не по запросу.

Правила хранения:

- Бэкап базы — ежедневно, храним 30 дней; недельный — 12 недель; месячный — 12 месяцев.
- Бэкапы шифруются (age или gpg), ключ хранится отдельно от бэкапов.
- Копия бэкапа в другой физической локации обязательна, но **в той же юрисдикции**.
- Восстановление проверяется раз в квартал на отдельном стенде; результат — запись
  в журнале с временем восстановления. Непроверенный бэкап бэкапом не считается.
- Удаление тенанта: данные вычищаются из основной базы сразу, из бэкапов уходят
  естественным истечением срока; в договоре это описано прямо, а не умалчивается.

Для клиента, которому нужна юридическая гарантия, — приложение к договору
с перечислением площадок и сроков.

### 16.3 Песочница тенанта: да, но узкая

**Решение.** Делаем **демо-тенант**, а не копию боевого.

Полная копия тенанта — дорогая и опасная затея: она тащит за собой персональные данные
живых людей, и через месяц «песочница» оказывается местом, где эти данные лежат
без присмотра.

Вместо этого:

1. **Демо-тенант** с выдуманными людьми и контентом, общий для всех.
   Ночной сброс к эталонному состоянию (`26` §9), ссылка на два часа для показа
   третьим лицам (`27` §6).
2. **Режим «Переглянути як роль»** в боевом тенанте (`24` §3.5) — администратор видит
   интерфейс глазами сотрудника, ничего не меняя. Это закрывает 90% случаев,
   ради которых просят песочницу.
3. **Черновики** у контента и назначений — новое можно собрать и посмотреть,
   не публикуя.

Чего не делаем: копирования боевых данных в отдельный тенант. Если клиент попросит —
предлагаем обезличенный слепок (имена заменяются, телефоны и почты вычищаются,
результаты сохраняются) как отдельную платную операцию, а не как кнопку в интерфейсе.

## 17. Эксплуатация

### 17.1 Сбой фоновых задач с 19.09.2026: что сделала выкатка и что осталось владельцу

С 19.09.2026 до выката миграции `0079_jobs_tenant_sources` круги `notification.dispatch`,
`attempt.expire` и `webhook.deliver` не обслуживали ни одного тенанта (§5, docs/v2/46). Решение
владельца продукта 25.09.2026: **старое не отправлять**. Выкатка делает это сама:

1. Миграция, до старта приложения и первого круга воркера: уведомления в `queued` со
   `scheduled_for` старше суток и доставки вебхуков в `pending` с `next_attempt_at` старше суток
   переводятся в `failed` с причиной «Не надіслано: збій фонової доставки з 19.09.2026; …» в
   `notifications.error` / `webhook_deliveries.response_body` — существующий статус и поле, нового
   значения перечисления нет. В колокольчике их нет: он показывает `sent`, `skipped` и `read`.
   Свежее, моложе суток, уходит как обычно.
2. Попытки миграция не трогает: их закрывает `attempt.expire` по постоянному правилу docs/12 §7
   п. 8 — результат, очередь проверки и журналы появляются, а закрытие, опоздавшее больше чем на
   сутки, не порождает ни уведомлений, ни вебхуков. Правило действует и при любом будущем простое
   воркера.

Осталось владельцу — переслать приглашения, которые не дошли. Запрос выполняется на проде ролью
`lola` (под `app_user` RLS не покажет ни одной строки), только чтение; повторный запуск
показывает тех, кому ещё не переслали:

```sql
-- Пропущенные приглашения: кому переслать «Надіслати запрошення» (docs/25 §17.1)
select t.name as space, t.slug, p.full_name, p.phone, p.email, p.invited_at
from (
  select distinct on (n.user_id) n.tenant_id, n.user_id, u.full_name, u.phone, u.email,
         n.created_at as invited_at
  from notifications n
  join users u on u.id = n.user_id
  where n.code = 'user_invited'
    and n.status = 'failed'
    and n.error like 'Не надіслано: збій фонової доставки%'
    and u.kind = 'employee'
    and u.status = 'invited'
    and not exists (select 1 from invitations i where i.user_id = u.id and i.accepted_at is not null)
    and not exists (
      select 1 from notifications later
      where later.user_id = n.user_id and later.code = 'user_invited'
        and later.created_at > n.created_at and later.status in ('queued', 'sent', 'read'))
  order by n.user_id, n.created_at desc
) p
join tenants t on t.id = p.tenant_id
order by t.name, p.full_name;
```

Каждому из списка — карточка человека → «Надіслати запрошення»: создаётся новое приглашение с
новой ссылкой. Повтор старого уведомления из журнала не годится — в нём ссылка, срок которой
(48 часов) истёк. Запрос проверяется `tests/integration/job-backlog.spec.ts` вместе с уборкой.
