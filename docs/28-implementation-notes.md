# Lola LMS — Заметки по реализации. Решения, отступления от ТЗ, открытые вопросы

Документ ведёт Claude Code по правилу «если ТЗ молчит или противоречит — не выдумывать, зафиксировать
вопрос». Здесь собраны решения по этапам 0–11 и то, что ждёт ответа заказчика.
Ссылки на PR — в репозитории `dmitriibraga2216-byte/Lola`.

## 28.1 Сквозные решения

| Тема | Решение | Где |
| --- | --- | --- |
| Дефолтные справочники тенанта (статусы целей, шкалы) | Не в миграции (`INSERT … FROM tenants` на чистой БД пуст), а в `server/db/tenantDefaults.ts` — вызывается сидом и `createTenant` | PR #10, #11 |
| Уникальность точек и подразделений | `locations(tenant_id, name)` — unique; импорт не создаёт подразделение с существующим именем (уникальность `org_units` по `path` пропускала кириллический дубль) | PR #11, #13 |
| Cookie `Secure` | По `X-Forwarded-Proto` (первое значение) или `COOKIE_SECURE`; за http-прокси не ставится | PR #10 |
| Типизированные роуты `$fetch` | При ~300 эндпоинтах Nitro упирается в TS2589: `useApi()` с явным типом опций, прямых `$fetch` в страницах нет | PR #14 |
| Нижняя панель кабинета | Четыре пункта по docs/05; остальные модули — строкой разделов на главной | PR #11 |
| Сессии | Логин через Google — тот же `createSession`, событие `login.google` в security_log | PR #14 |

## 28.2 По этапам

### Этап 7 — развитие (docs/19)
- Целевой уровень цели по компетенции по умолчанию = требуемый уровень профиля (или текущий + 1).
- Заявка на карьеру завершается на шаге HR (`approved`); связь с модулем оценки — через `assessment_id`, отдельного шага «оценка» нет.
- Достигнутая цель по компетенции создаёт оценку компетенции `source=manager` от того, кто поставил `achieved`.

### Этап 8 — оценка и чек-листы (docs/20)
- Калибровка (§7.9): руководитель правит свою оценку только с комментарием, запись в `audit_log` (`assessment.calibrate`); отдельной таблицы нет.
- Маппинг оценки на уровень компетенции (§7.6): доля от максимума шкалы × число уровней компетенции; приоритет — оценка руководителя, иначе средняя.
- Офлайн-режим чек-листа: черновик и фото (сжатые до 1280px) в `localStorage`, отправка при `online`, время начала/конца — фактическое.
- **Открыто:** подпись проверяемого (`require_signature`) и одноразовая ссылка тайного покупателя без входа — в схеме есть поля, UI не делался; нужно решение по формату подписи и безопасности анонимной ссылки. Сейчас тайный покупатель — обычный чек-лист `kind=mystery` под сотрудником со скоупом `checklist.run`.

### Этап 9 — занятия, вебинары, комплексные тесты (docs/18)
- Вебинар — `meetups.kind=webinar` + расширение `webinars` (1:1); событие хаба — `kind=event`.
- QR: токен `meetupId.окно.HMAC(секрет занятия)`, окно 30 с, принимаются текущее и предыдущее; отклонённые попытки — в `audit_log`.
- Конфликт расписания (§7.9): предупреждение в ответе `register`, не запрет.
- Оценка занятия после `finished`: уведомление `meetup_feedback_request` + существующий модуль опросов; отдельного экрана нет.
- **Открыто:** занятие как урок курса (§7.7) — регистрация хранит `enrollment_id/lesson_id` и при `attended` зачитывает урок, но тип урока `meetup` в редакторе курса не добавлен: как оно выглядит в дереве курса?
- Комплексный тест: попытки частей идут через `attempts.startAttempt`, поэтому лимит попыток самого теста тоже действует.

### Этап 10 — хаб (docs/03 §3.22, §3.26)
- Объявление = новость `kind=announcement`: модально при входе на всех страницах кабинета до «Ознайомився»; сканер напоминает, после срока — руководителю точки список.
- Wiki: права `view_roles/edit_roles` наследуются по ветке; пусто у корня = видят все, правят `wiki.edit`.
- Конструктор отчётов: поля и фильтры только из белого списка в `reportBuilder.ts`; расписание — отправка уведомления со ссылкой на xlsx (файл в канал не вкладывается).
- R3 (форум, чат, контакты, дни рождения, бонусы, магазин, задачи) — не начат.

### Этап 11 — интеграции (docs/09)
- OAuth: `oauth_states` в БД, колбек ищет state SECURITY DEFINER-функцией (окно без cookie), `refresh_token` только шифротекстом AES-GCM, `access_token` не хранится.
- Провайдеры: Google (Calendar, Meet, Directory, вход), Zoom (встречи, отчёт участия). Ключи приложения — env (`GOOGLE_CLIENT_ID/SECRET`, `ZOOM_CLIENT_ID/SECRET`, `APP_URL`).
- Zoom-посещаемость запускается вручную (`sync-meetup`), не задачей через час после окончания.
- **Открыто:** видео с Google Диска (§9.1) — как встраивается в блок урока; ротация ключа шифрования (§9.4) — не делалась.

### docs/15 (правила по эталону) и docs/17 (программы)
- Правило = фильтр аудитории + опциональные действия; программа с режимом `automation` назначается при срабатывании правила (`assignProgramsForRule`), задержка правила → `available_from` зачисления, открывает ежедневный `programScan`.
- Программа и траектория — одна сущность `programs.mode`; для linear рёбра выводятся из порядка узлов.
- Условие перехода `position_is` принимается схемой, но при движении по графу трактуется как «пройдено»: позиция человека проверяется правилом на входе, а не на ребре — уточнить, нужен ли выбор ветки по должности внутри траектории.
- Заявка через каталог (`catalog_request`) решается тем, у кого есть `assignment.create` (`POST /program-enrollments/:id/decide`); уведомление уходит руководителю точки.
- Сертификат программы (`certificate_template_id`) не выдаётся — сертификаты пока только у курсов (docs/14); нужно решение о шаблоне для программы.
- Попытки частей-тестов внутри программы создаются обычным `startAttempt`, поэтому действует лимит попыток самого теста.

### docs/16 (люди, оргструктура, справочники, импорт)
- ФИО хранится и по частям (`last_name/first_name/middle_name`), и собранным `full_name`; старые записи разобраны миграцией по пробелам (`split_part`) — при трёх и более словах последнее слово считается отчеством. Стоит проверить глазами после миграции прода.
- Блокировка (`is_blocked`) = `status=suspended` + отзыв сессий; обучение не снимается. Архивирование закрывает размещения (`ended_at`), снимает незавершённые записи, отзывает роли; сертификаты по публичной ссылке остаются.
- Последний администратор (роль `admin` на весь тенант) защищён во всех трёх операциях — блокировка, архив, снятие роли — ответ `409 last_admin`.
- Слияние дублей переносит строки в 10 таблицах (записи, попытки, сертификаты, воркшопы, занятия, программы, компетенции, цели, просмотры, уведомления); дубль архивируется, телефон/почта/внешний № освобождаются, в `comment` пометка «Обʼєднано з …».
- Удаление по запросу (GDPR): только `settings.tenant`, ФИО → «Користувач #xxxxxxxx», контакты и дата рождения в null, заметки удаляются, результаты обучения остаются обезличенно.
- Импорт: сопоставление колонок угадывается по синонимам заголовков (`guessMapping`), пресет хранится в `tenants.settings.importPresets.default` и применяется автоматически при совпадении заголовков; строка без телефона, но с `external_id` — создаётся `invited` с предупреждением; опция `archiveMissing` не трогает администраторов и инициатора. Применение синхронное в запросе с прогрессом в `stats.processed` (UI опрашивает), а не отдельной pg-boss задачей — при 5000 строк укладывается в таймаут; вынести в очередь, если появятся файлы крупнее.
- Справочники: удалить используемое значение нельзя (`409 in_use`, счётчик), есть деактивация (`is_active` у міст/посад/точок) и слияние (`POST /refs/:kind/merge`); подразделения не сливаются — только перенос (перетаскивание в дереве пересчитывает `ltree`-путь потомков).
- Динамические группы пересчитываются в `assignment.sync` (ежечасно) перед раскрытием аудиторий; `people_inactive` — ежедневно в `due.scan`, админам раз в месяц (dedup по месяцу).
- Массовые действия из списка выполняются последовательно с построчным отчётом об ошибках; «назначить обучение» ведёт на экран назначений с `userIds` в query.
- **Открыто:** срок действия роли и причина при назначении (§6.2) — в схеме `user_roles` полей нет, форма не расширялась; журнал безопасности `/security-log` (§5.5) существует со стадии 0, фильтры по человеку/типу/периоду не добавлялись; «Скинути привʼязку Telegram» обнуляет `telegram_chat_id`, канал вернётся на SMS.
- Попутно: `app/pages/admin/reports.vue` затенял дочерние маршруты (`/admin/reports/builder` не открывался) — перенесён в `reports/index.vue`.

### docs/19 (развитие) — часть 2
- Курс закрывает разрыв (Б.4, вариант «в»): у курса поля `competency_id/competency_level`; оценка `source=test` ставится при завершении курса, только если в курсе есть урок-тест и у человека есть сданная попытка по нему; если уровень уже не ниже — ничего не пишется.
- Порог суммы заявки (§7.7): `tenants.settings.development.externalTrainingThreshold` (по умолчанию 5000); выше порога после HR статус `hr_approved`, решает `settings.tenant`; администраторам уходит `request_new`. Маршрут не настраивается произвольно — только этими двумя шагами.
- Согласование целей (§7.4): `settings.development.goalsNeedApproval`; цель, поставленная самим человеком, ждёт руководителя (`approved_at`), до этого не двигается по статусам (`409 goal.not_approved`); «Повернути» требует комментарий.
- Закрытие ИПР (§7.6): ежедневный `planPeriodScan` в `due.scan` — за 7 дней напоминание владельцу, после `period_to` цели без финального статуса → первый статус `is_final and not is_success` (по умолчанию «Не досягнуто»), план → `review`.
- Карьерная заявка (§7.9): при `approved` назначается обязательный контент профиля целевой должности (`assignments.kind=career`, аудитория — один человек); цикл оценки готовности создаётся только если в настройках задана анкета (`careerAssessmentFormId`), оценщики self+manager, 14 дней.
- «Застосувати профіль» (§5.5): создаёт назначения `kind=position_profile` с аудиторией «должность»; повторное применение переиспользует существующие назначения.
- Матрица (§5.6) и отчёт «Готовність до підвищення» считаются в приложении (не SQL) — до ~300 людей на точку это быстро; для сети на тысячи людей понадобится витрина.
- Категории компетенций — отдельный справочник `competency_categories` (раньше ссылались на категории курсов; старые ссылки обнулены миграцией 0020).
- Стратегические планы (§3.8) — CRUD без связи с бюджетом заявок: подсказка «бюджет підрозділу на квартал» в форме заявки (§6.2 `[решение]`) не делалась — нет правила, какой план считать бюджетом подразделения.

### docs/20 (оценка) — часть 2
- Подпись (Б.1): компонент `SignaturePad` (canvas, палец/мышь) → PNG в медиа как обычное фото; сервер отказывает `signature_required`, если `require_signature` и подписи нет; в карточке прогона подпись показывается картинкой. Для прогонов тайного покупателя подпись не требуется.
- Тайный покупатель (Б.2): `mystery_waves` (волна = период + чек-лист `kind=mystery`, статусы active/published/closed) и `mystery_links` (одноразовая ссылка на точку, хэш токена, 24 часа). Публичные `/api/v1/public/mystery/:token` и страница `/m/:token` без входа; прогон создаётся сразу завершённым от имени выдавшего ссылку с `is_external=true, wave_id`; фото по ссылке не загружаются (медиа требует сессии). До публикации волны прогон видят только `report.tenant` (карточка → 404, отчёт чек-листов и отчёт «волны × точки» скрывают). Ссылки выдают только руководители сети.
- Попутно: `/api/v1/media/:id?redirect=1` — 302 на подписанную ссылку; раньше фото чек-листов ссылались на JSON-ответ и не отображались.

### docs/21 (хаб) — R1/R2
- Объявления остались `news.kind=announcement` с полями `show_mode/priority/block_until_ack/ack_text` и периодом `publish_at/unpublish_at` (отдельной таблицы `announcements` из §3.3 нет — данные и отчёты общие с новостями). События — `meetups.kind=event` (+`cover_key`, `registration_required`, `guests_count` у записи).
- Правило чтения (Б.5): клиент шлёт `POST /news/:id/view {seconds, scrolledToEnd}` каждые 5 с и при прокрутке; `ack` отвечает `422 news.too_fast / not_scrolled`, пока не набрано 10 с и прокрутка. Для сервисных вызовов есть `force`.
- `block_until_ack` (Б.6): галочка доступна только `settings.tenant`; интерфейс перекрыт, крестика нет; исключения — вход и `/profile`.
- Поиск (§7.1): заголовок ×3 (ilike), FTS ×2, семантика ×1; источники «статья / урок / вопрос теста» (вопросы — ilike по тексту stem, без индекса); статьи вне аудитории (`visibility.scope=audience` + конструктор) не показываются вовсе; каждый запрос пишется в `search_queries` (отчёт «запити без результату» за 90 дней).
- Актуальность (§7.2): `review_at` → владельцу `knowledge_review_due` (раз на дату); плашка «Потребує перевірки» = `review_at` старше 30 дней без подтверждения; «Підтвердити» ставит следующий срок +180 дней. Уволился владелец → статьи переходят тому, кто архивирует, с пометкой.
- Wiki: блокировка страницы на 15 минут (`POST /wiki/:id/lock`, `{release:true}` снимает), сохранение снимает; diff — построчный LCS по плоскому тексту блоков, не по HTML.
- Комментарии к новостям: флаг `comments_enabled` хранится, самих комментариев нет — это R3 вместе с форумом.

### docs/23 (уведомления)
- Правило канала (§4): Telegram → SMS (только обязательные коды и при наличии телефона) → in-app. In-app — это сама строка `notifications` (статус `skipped/no_channel` тоже видна в колокольчике); отдельного канала `inapp` в шаблонах нет.
- Обязательность (`is_mandatory`) по умолчанию задаётся регуляркой `MANDATORY_DEFAULT` (дедлайны, аттестации, объявления, безопасность, приглашение); тенант переопределяет в шаблоне.
- Дневной лимит (Б.9): 10 в сутки, обход — `BYPASS_DAILY_LIMIT` (`*_due_today`, `*_overdue`, `*_expiring`, `assessment_*`, `announcement_*`, `security_*`, `user_invited`, `import_*`) и `urgent`. Троттлинг по коду — `throttle.maxPerDay` в шаблоне.
- Дедуп: `dedup_key` уникален — повторная постановка молча возвращает `false`, строки `skipped: duplicate` нет (иначе нарушится уникальность).
- Тихие часы — по таймзоне точки человека, иначе тенанта; перенос помечается `skip_reason=quiet_hours` при статусе `queued` (§13.1).
- Ретраи (§6.5): 1/5/25/60/180 минут, после пятой — `failed`. Telegram 403 и «chat not found» → `users.telegram_blocked=true` (chat_id остаётся; новая привязка снимает флаг), руководителю `telegram_blocked_manager`, обязательное — сразу SMS.
- Эскалация (§6.6): `escalate_after_hours` у шаблона; реакция = клик «Пройти» (`/tg/go?n=`) или прочтение в колокольчике. Сканер ежечасно в `assignment.sync`.
- Автологин `{{link}}`: кнопка «Пройти» ведёт на `/tg/go?to=<путь>&c=<chat>&n=<id>` — токен создаётся при клике (10 минут, одноразовый), а не заранее в тексте, чтобы ссылка в истории чата не жила вечно.
- Кнопки бота: «Відкласти на день» — максимум дважды (`payload.snoozed`), «Не нагадувати» — только необязательные (пишет `user_notification_prefs`); `/menu`, `/help`, `/stop`.
- Версии шаблонов: правка текста создаёт `notification_template_versions`, отправленное хранит `template_version`; `DELETE` шаблона = «Повернути стандартний».
- Отчёт «Реакція» считает клики по «Пройти» и прочтения; открытие ссылок из SMS/e-mail не отслеживается.
- Push (§4) — R2, не делался; `telegram.health` — getMe раз в час в лог/метрики без UI-индикатора.

### docs/22 (отчёты) — каркас, выгрузки, журналы
- Плитки со сравнением считаются на лету по равному предыдущему интервалу (`previousPeriod`); для снимков (люди, «не готовы», сертификаты) сравнения нет — исторических витрин нет. Матвью каждые 10 минут (§7.6) не делались: объёмы Каппі не требуют, «Розраховано зараз» показывать нечего.
- «Прогрес навчання» по предмету: курс/программа/тест/практикум/занятие/опрос — одна воронка «назначено → начали → завершили → с первого раза» с собственным толкованием шагов для каждого предмета (для занятия «с первого раза» = пришёл, для опроса = ответил).
- «Контент»: оценка курса берётся из первого вопроса опроса `course_feedback`, привязанного к курсу; «где отваливаются» — урок с наибольшим числом незавершённых прогрессов.
- Выгрузка: `POST /reports/:name/export` всегда ставит задачу `report.export` (порог 5000 строк не проверяется — фон дешевле, чем ждать); файл в S3 `exports/<tenant>/<id>.<xlsx|csv>`, ссылка подписанная, 24 часа, после — `file_key` обнуляется (объект чистит lifecycle бакета). Прямая `?format=xlsx` осталась для маленьких таблиц.
- Журналы `/logs/:kind`: протокол статусов — это `audit_log` с `before/after.status`; сессии/уведомления/безопасность/импорт/автоматизация/интеграции — свои таблицы; `logs.retention` ежедневно удаляет старше срока (3 г / 1 г / 90 дн по §5). Выгрузка журнала — JSON по тем же фильтрам (xlsx не делался).
- Дайджест руководителю (§8): по понедельникам в `due.scan`, по каждой точке с руководителем, dedup по неделе.

### Паритет 4 — активная роль в сессии, срок и причина роли, «должность → роль» (`01` §1.9.2–1.9.3, `29` Б.15)
- `sessions.active_role_id` (миграция 0028). Права считаются **только по активной роли**: `loadAccess` берёт области (`grants`) активной роли, а не объединение всех ролей; `/auth/me` отдаёт `activeRole`, `roles` (все действующие) и `scopes` активной роли. API-токен активной роли не имеет — скоупы токена на весь тенант, как и раньше. Старые сессии получили роль по умолчанию миграцией; если записанная роль снята или истекла, `resolveActiveRole` подменяет её на роль по умолчанию и пишет в сессию.
- **Роль по умолчанию при входе** (`01` не задаёт порядок — решение): от самой широкой к самой узкой, обратный порядок таблицы `01` §1.2 — `admin` → `author` → `manager` → `mentor` → свои роли тенанта → `employee`; внутри ранга — по имени. Наставник, который ещё и учится, входит наставником и переключается на «Співробітник», когда хочет видеть кабинет. Политика тенанта «Роль за замовчуванням» (`24` §3.4.1) — это роль для новых людей, не активная; появится с `spec-24`.
- `POST /me/role/switch {roleId}` — только среди своих действующих ролей: чужая, снятая, истёкшая → 403 `forbidden` (по `04`: нет прав на роль), по API-токену → 400. Та же роль — `changed: false`, без события. Событие `role.switch` в `audit_log`: `before` = старая роль, `after` = новая, `request_context` из хелпера.
- **Аудит с обеими ролями**: `audit_log.actor_role_id` (активная в момент действия) и `actor_roles text[]` (коды всех действующих) — `recordAudit` берёт их из `Access` текущего запроса через `currentEvent()`; вне запроса (фоновые задачи) — null. Колонки добавлены в `02`.
- `user_roles.valid_until`, `reason` (`16` §6.2, `29` Б.15): истёкшая роль не входит в `effectiveRoles` — не даёт прав, не участвует в переключении и не считается при защите последнего администратора (`isLastAdmin`). Ежедневный `expireRoles` в `due.scan` удаляет истёкшие строки с событием `role.expire`. Повторный `POST /people/:id/roles` той же роли в той же области — редактирование срока и причины (`role.update` с `before`/`after`), снятие — `DELETE …?reason=` (`role.revoke` с причиной). `validUntil` принимается датой (конец дня UTC).
- `position_role_map` (0028, RLS): правило «должность → роль» одно на сеть, `scope_id null` при `location`/`org_unit` означает область основного размещения. Применяется в той же транзакции при `addPlacement` с `is_primary` (включая массовое «перевести на точку») и при импорте после вставки размещения. Выданная роль помечена `user_roles.is_org_derived` (флаг по аналогии с группами `16` §3.3, мокап PersonCard: «Видана автоматично за правилом «посада → роль»»); при следующей смене должности производные роли, которых правило больше не даёт, снимаются (кроме последнего администратора), ручные не трогаются, ручное переназначение снимает флаг. `PUT /settings/position-role-map` меняет карту целиком, но **не** пересобирает роли всей сети сразу — только при следующей смене должности/импорте (иначе один PUT перекроил бы права всех без предупреждения); экран настроек карты — `spec-24`. Импорт по-прежнему выдаёт роль из колонки `role` (или `employee`) руками — правило добавляет к ней производные.
- Клиент: карточка человека в сайдбаре админки по мокапу Main — имя, активная роль, шеврон; в меню — список ролей с активной (radio), переход по клику; в кабинете — чипы ролей в профиле. После переключения профиль перечитывается и экран уходит на стартовую под новую роль (`homeFor`), потому что текущий раздел под новой ролью может быть недоступен. Вкладка «Ролі» карточки человека: область, срок («безстроково» / «Діє до …» / «термін минув»), признак «видана автоматично», причина, дата выдачи; форма — роль, область, срок, причина; снятие — строка с причиной и подтверждением.
- Открытые вопросы: (1) фоновые выгрузки отчётов (`reportExports`) считают область по роли по умолчанию, а не по роли, активной в момент запроса, — если это важно, хранить `active_role_id` в задании выгрузки; (2) экран `position_role_map` в настройках (`24` §3.4.1 «Режим призначення ролей: Зіставлення посад») и кнопка «пересобрать роли по всей сети» — не делались, мокапа нет; (3) уведомление человеку об истечении роли — нет в `16` §8, не добавлено.

- **Одиннадцать типов контента.** `POST /tasks` принимает любой `content_type` из `02`; проверка существования и доступности контента — `server/services/taskContent.ts` (`findContent`/`listContent`): курс, программа, ресурс, практикум — только опубликованные; тест — не удалённый; комплексный тест, анкета оценки, чек-лист — активные; опрос — не закрытый; заняття/вебінар — `meetups.kind` (`webinar` ↔ `meetup|event`), не отменённые. Записи (`enrollments`/`program_enrollments`) по-прежнему создаются только для курса и программы: `enrollments.subject_id` ссылается на `courses`, для остальных типов «призначено» = раскрытая аудитория назначения (правила подхватываются при старте попытки, `taskParams.ts`). Долг: единая таблица записей для всех типов — `spec-12`/`spec-18`/`spec-20`, где появятся прохождения тестов, занятий и опросов.
- **Пять групп параметров** (`15` §14.3) — `shared/schemas/assignments.ts`: `taskParamsSchema` — `z.discriminatedUnion('contentType', …)` из одиннадцати `strict()`-объектов; группы Термін · Результат · Нагороди · Інші — общие, «Загальне» зависит от типа (тест — полный набор с подгруппой «Питання», курс — `strictOrder`/`allowEarlyFinish`, программа — `strictOrder`, комплексный тест — спроби/пауза/`showScore`, практикум — спроби, вебінар — `webinarMinWatchPct`, остальные — ничего). `PARAM_KEYS_BY_CONTENT_TYPE` теперь выводится из union, а не дублируется руками. Чужой для типа ключ (`attemptsAllowed` у курса) — 400 с текстом, какое поле недоступно. `PUT /tasks/:id/params` берёт тип из назначения, тело без `contentType`.
- **«Метод призначення»** хранится колонками по `02`: `assignments.via_catalog`, `automation_rule_id` (FK, `set null`), `use_in_dev_plans`; в API — те же ключи в теле params (`methodGroupSchema`), в `params jsonb` не пишутся. Поведение флагов (доступ через каталог, использование в планах развития) — долг `spec-10`/`spec-19`.
- **Напоминания Г-15.1** — модель `{enabled, beforeDueDays[7,3,1], onDueDate, afterDueEveryDays=3, afterDueMaxCount=5, escalateToManagerAfterDays=7, channel=null, notifyOnAssign}`; миграция 0029 переводит старые ключи (`beforeDays`, `afterDays[0]`→шаг, `channels[0]`→`channel`, `notifyManagerAfterDays`). `due.scan`: после срока шлёт в дни, кратные шагу, не больше `afterDueMaxCount` раз (dedup `overdue:<id>:d<N>`); руководителю — один раз на запись, когда просрочка ≥ порога (dedup без даты). `channel=null` — канал по умолчанию человека. Модалка «Нагадування» эталона (состав полей не снят) — группа «Нагадування» на экране параметров.
- **Аудитория** (`15` §14.4): `GET /tasks/:id/audience` — все активные люди с вкладками Всі/Призначено/Не призначено и фильтрами эталона (посада, місто, точка, підрозділ, мітка, рівень, дата реєстрації/призначення, спосіб). Три способа назначить: `{userIds[]}` («Призначити вибраним»/по строке), `{filter}` — конструктор из четырёх измерений (`city|position|org_unit|tag`, режим `any|include|exclude` = «Будь-яке/Обрані/Всі, окрім», как у правила автоматизации), CSV. Все три растят правило `type=user` в `audience` и убирают людей из `exclude`; снятая ранее запись открывается заново. Снятие `DELETE /tasks/:id/audience/:userId` — `cancelled_at` у записи + человек в `exclude` (иначе sync вернул бы его), данные не удаляются.
- **«Спосіб призначення»** — отдельного перечисления в `02` нет, значение выводится: `enrollments.source` (`self|catalog`→«Самостійно», `import`→«CSV», `repeat`) поверх `assignments.kind` (`task_type`: `manual`→«Вручну», `auto`→«Правило», `trajectory`→«Траєкторія», `catalog`). Вопрос: нужен ли эталонный список значений колонки — при уточнении заводится перечисление в `02`.
- **CSV Г-15.4** — переиспользован разбор `parseImportFile` из импорта людей; ключ по заголовку (`email|e-mail|пошта`, `phone|телефон`, `external_id|зовнішній №`), необязательные `due_at|дедлайн|термін`, `starts_at|старт|початок` (ДД.ММ.РРРР или ISO); UTF-8, при символах замены — Windows-1251. Предпросмотр пишет протокол `import_jobs kind=task_audience` (`status=ready`), применение — `POST …/import/:jobId` (повторно — 409), сроки из файла — в `enrollments.due_at/starts_at` записей курса.
- **Г-15.2 `on_leave_condition`** — на `automation_rules` (по `02`) **и** на `assignments` (решение: конструктор аудитории в Lola живёт и в разовом назначении, `15` §14.4): `keep|cancel_unstarted|cancel_all`, CHECK. `applyOnLeave` вызывается из `syncAssignments` после раскрытия: условие — аудитория назначения, у назначения правила (`automation_rule_id`) — условия правила (`matchesConditions`); снятие — `cancelled_at` + `cancel_reason='left_condition'` + событие + аудит без актора. Назначение, создаваемое правилом, наследует `on_leave_condition` и получает `automation_rule_id`. Работает для записей курса; программы — долг `spec-17`.
- **Г-15.3** — `assignment_competencies` (M2M, RLS), `PUT /tasks/:id/competencies`, счётчик в списке и «Компетенції: N» в шапке карточки. Подтверждение компетенции при успешном завершении (источник `assignment`, `19` §5) — долг `spec-19` (нет `user_competencies.source`).
- **Доп. параметры §14.5** — `task_parameters` (`kind text|select|number`, CHECK, `unique(tenant_id, name)`) и `task_parameter_values(task_id, parameter_id, value jsonb)`; обе с `tenant_id` и RLS (в `02` у значений `tenant_id` не указан — добавлен ради правила 1). Значения проверяются по типу параметра, обязательный не может быть пустым. Экран справочника `/manage/tasks/parameters-v3` — долг (API есть, UI нет).
- **Баннер «N завдань було змінено»** (`15` §14.6) — `assignments.content_changed_at` ставится внутри транзакции публикации курса (`publishCourse`) и изменения состава теста (`setQuizQuestions`) для активных/приостановленных назначений этого контента; «изменённые» = `content_changed_at > content_change_notified_at`. `POST /tasks/changed/notify` шлёт `assignment_content_updated` всем назначенным, кроме завершивших (dedup на день), `dismiss` снимает баннер без рассылки; оба — в аудит. «Керувати сповіщеннями» ведёт на шаблоны. Остальные типы контента (ресурс, практикум, …) пока не помечают — вопрос, что считать «изменением» у них (новая версия ресурса — `spec-11`).
- **Экраны**: список по мокапу Main (`/tasks?type=`, меню «Додати призначення» из 11 типов, баннер, СТАН = «ВИКОНАНО», когда все назначенные завершили), карточка `[id]/index.vue` из четырёх блоков (люди ушли на экран аудитории, действия над назначением — в шапке), `[id]/params.vue` — боковое меню пяти групп + «Нагадування», `[id]/audience.vue` — вкладки, фильтры, конструктор, CSV. «Створити новий» из блока «Контент» — долг (ведёт на «Обрати з існуючих»). `new.vue` — тип из `?type=`, контент по типу, параметры задаются после создания.
- Пути `/tasks/...` по `04` §4.9 введены рядом со старыми `/assignments/...` (снятие старых — `spec-04-routes`).

### Spec 12 — вопросы и попытки по эталону: группы, метод подсчёта, очередь по ответам, запросы попыток, пересчёт (`12` §14, `32` Б.6)
- **Коды типов вопросов — из `02`** (`30` §3 п. 3): `single | multi | free | ordering | classification | comparison | answer_by_map | number | text_short | file`. Миграция 0030 переименовывает старые коды Lola (`multiple→multi`, `order→ordering`, `match→comparison`, `text_long→free`) в `questions.kind` **и** в поле `kind` внутри `attempts.snapshot` — это техническое переименование кода, содержание снимка (формулировки, варианты, эталоны) не меняется, правило 4 не нарушено. CHECK на `questions.kind`; перечисления `question_kind`, `scoring_method`, `attempt_request_status` добавлены в `02` и `shared/enums.ts`.
- **`scoring_method` заменяет `partial_credit`**: миграция переносит значение (`true→formula`, `false→all_or_nothing`) и удаляет колонку; для старых снимков `scoringMethodOf()` читает `partialCredit`. Метод действует на `multi`, `ordering`, `comparison`, `classification`, `answer_by_map` (решение `12` §14.6 — распространить и на те типы, где в эталоне переключателя нет). `negative_marking` — только у `multi` и `answer_by_map`.
- **Группы вопросов** (`question_groups`, `questions.question_group_id`, FK `set null`): при `questions_mode=one_per_group` из назначения снимок берёт по одному случайному вопросу из каждой группы, вопросы **без группы входят все** (решение: иначе автору пришлось бы раскладывать по группам и «общие» вопросы); `limited` — случайные `questions_count`. Выбор фиксируется в снимке (`groupId`), «Кількість питань» на стартовом экране считается по группам. Для `selection_mode=random` режимы игнорируются — там свои правила отбора. Удаление группы вопросы не трогает.
- **`classification`**: `options {groups[{id,title}], items[{id,text}]}`, эталон `answer {placements[{itemId, groupId}]}` — верный класс не хранится в `options` (иначе он утекал бы ученику через `stripAnswers`); в `12` §3.3 п. 10 записано `items[].group_id` — принят вариант с эталоном в `answer`. **`answer_by_map`**: области в долях 0..1 (`rect`/`circle`, Г-12.1 п. 2), эталон `{areaIds}`; ответ — `{areaIds}` (кнопки-области поверх картинки, доступно с клавиатуры) либо `{points[{x,y}]}` — точка попадает в первую содержащую область.
- **`grader_hint`** живёт в снимке (нужен проверяющему по состоянию на момент попытки), из выдачи ученику вырезается `stripAnswers` вместе с `answer`/`explanation`. **Вложения к free**: `questions.attach_files`; файл идёт через `/media` (presigned PUT), затем `POST /attempts/:id/answers/:questionId/files` кладёт `{mediaId, name, kind, bytes}` в `attempt_answers.answer.files` (не больше 5); для `file` — всегда разрешено.
- **Очередь по ответам** `GET /review/answers` (`12` §14.4): вкладки `checked=unchecked|checked|all`, метки вопроса (`questions.tags &&`), «Поза курсами» = `attempts.lesson_id is null`, «Поза програмами» = тест не является узлом ни одной программы, точка — основное размещение человека. Старый `/review/queue` остался как «непроверенные». Своя работа в очередь не попадает.
- **Запросы попыток** (`attempt_requests`): создаются только когда попытки действительно исчерпаны (иначе 422), один `pending` на человека и тест (409). Решение — скоуп `review.grade` (наставник/руководитель/методист), себе решать нельзя. Одобрение = +1 попытка: `effectiveAttemptsAllowed = attempts_allowed + число одобренных запросов`; `assignments.params` не меняется, в `attempt_requests` фиксируются `attempts_used/attempts_allowed` на момент запроса. Уведомления `attempt_request_created` (тем, у кого `review.grade` по тенанту или точке человека) и `attempt_request_decided`. Кнопка «Попросити ще одну спробу» — на экране исчерпанных попыток (`12` §14.5). Значение `rejected` («Відмовлено») снято не с экрана, а с кнопки «Відмовити» `12` §6.3 — **вопрос заказчику: есть ли в эталоне третье значение фильтра «Статус»**.
- **«Перерахувати»** (`22` §13.7, `attempt_results`). Пересчитывается: автопроверяемые ответы по **текущим** `answer`, `scoring_method`, `negative_marking`, баллу (с `quiz_questions.points_override`) и критичности вопроса; итог, статус (`passed/failed/review`), `max_score`. Не трогается: `attempts.snapshot` (формулировки, варианты, порядок), ответы ученика, оценки наставника по `free`/`file` (только ограничиваются новым весом), `attempts.params`. Каждый пересчёт — строка `attempt_results(reason=recalculate, comment, created_by)` и `audit_log attempt.recalculate` с before/after; первый подсчёт и итог ручной проверки тоже пишутся (`submit`, `review`). Есть `POST /tests/:id/recalculate` по всем завершённым попыткам. Если вопрос-ключ был копией (Г-12.2), пересчёт видит именно её. Долг: пересчёт не трогает `lesson_progress`/сертификаты при переходе passed→failed — только failed→passed завершает урок.
- **Копия / ссылка** (Г-12.2): `POST /tests/:id/questions/import` `{mode: copy, fromQuizId, questionIds}` создаёт независимые записи в **том же банке**, что источник (у теста своего банка нет; отдельного `source_question_id` не заводим — источник в `audit_log question.copy`), `{mode: link, questionIds}` добавляет ссылку на запись банка; повторная ссылка не дублирует. `version` вопроса растёт при правке содержания или ключа (stem, options, answer, scoring_method, negative_marking, points), а не только эталона; редактор предупреждает, если вопрос уже есть в снимках (`GET /questions/:id → inSnapshots`).
- **Протокол** — экран `TestResult`, не PDF: `GET /attempts/:id/result` отдаёт `protocol: shown | hidden | after_last_attempt` по трём переключателям назначения (`show_error_protocol`, `hide_correct_in_protocol` — `answer` не отдаётся, `protocol_after_last_attempt` — при незачёте и оставшихся попытках список вопросов пуст), плюс `earned/maxScore/attemptsAllowed/attemptsLeft` для строки «Поріг · бали · спроба». «Помилки — N» показывает только неверные с «Ви відповіли … правильно — …».
- **Экраны**: `/admin/questions/new|:id` (QuestionEditor: чипы семи типов эталона + три Lola, конструкторы по типу, справа группа/метод/бали/мітки), редактор теста (группы, три способа добавления, «Перерахувати»), `/admin/quizzes` (ContentTests), `/admin/review` (ReviewAnswers), `/admin/review-workshops` (чипы ReviewQueue с счётчиками), `/admin/attempt-requests` (AttemptRequests; в меню «Навчання»), `/learn/quiz/:id` (Test: «Одна правильна відповідь · N бали», «Пропустити / Відповісти»; TestResult: карточка результата, «Помилки — N», «Повторити»; экран исчерпанных попыток с запросом), Workshop — «Що перевіряє наставник», «Ще фото». Долги: у `answer_by_map` области задаются числами, а не рисованием на картинке; «Скільки варіантів можна обрати» у `multi` — вычисляется по числу верных, отдельного поля нет; `cloze` — R2.
