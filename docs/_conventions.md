# Соглашения для всех модульных документов ТЗ Lola

Этот файл читают авторы модульных разделов. Он не входит в поставку как отдельный документ,
но определяет форму всех файлов `docs/1x-*.md` и `docs/2x-*.md`.

## Контекст продукта

Lola — мультитенантная SaaS-LMS для линейного персонала сетей (кухня, зал, склад, точки).
Первый тенант — Каппі (Одесса, две точки). Функциональный ориентир — LMS Collaborator 2.43
(инсталляция `bulochki.davintoo.com`); копируется функциональность, не код и не вёрстка.
Контент эталона не переносится.

## Технические рамки (не переписывать, только соблюдать)

- Nuxt 3 + Nitro, TypeScript; Postgres 16 + pgvector; Drizzle ORM; pg-boss; S3 (MinIO).
- Мультитенантность: `tenant_id` в каждой таблице, RLS, доступ только через `withTenant()`.
- Вход: телефон + OTP (Telegram/SMS), сессии в httpOnly cookie. Пароль — резервный способ.
- Права: скоупы (`course.edit`, `review.grade`, …), роль = набор скоупов, назначается в области
  (тенант / подразделение / точка). Подробности — `docs/01-roles.md`.
- API: `/api/v1`, JSON, `{data}` / `{error:{code,message,details}}`, курсорная пагинация,
  zod-схемы в `shared/schemas`, идемпотентность мутаций по `Idempotency-Key`.
- Языки интерфейса uk (основной) и en; все строки — через i18n-ключи.
- Бренд: беж `#F0E7D7` фон, крем `#FAF6EC` карточки, солнце `#FFC933` — действие,
  бирюза `#2BBFAE` — прогресс и результат, коралл `#FF6B4A` — ошибка, чернила `#0C0F14` — текст.
  Шрифт Nunito (заголовки 900), радиусы 16–36, теней нет, mobile-first.
- Всё, что меняет чужие данные, пишется в `audit_log`.

## Факты, снятые с эталона (использовать как требование)

- Правила прохождения (попытки, проходной балл, лимит времени, сроки) задаются **в назначении**,
  а не в самом тесте. В карточке теста — только состав вопросов и описание.
- Назначение («Завдання») — самостоятельная сущность: тип (вручну / автоматично / за каталогом /
  за траєкторією / архів), автор, метки, даты создания, старта и завершения, список людей,
  связь с ИПР и компетенциями; две группы настроек — «Параметри» и «Нагадування».
- Правила автоматизации в эталоне названы по должностям («Бариста», «Менеджер»,
  «Всі працівники компанії») — по сути профиль обучения должности.
- Редакторы контента разделены на вкладки «состав» и «описание и настройки».
- Роли переключаются самим пользователем в меню профиля: Адміністратор, Тьютор, Користувач,
  Адміністратор Т.Т. (администратор точки). У человека может быть несколько ролей сразу.
- Загрузка обложки: 16:9, форматы jpg, png, jpeg, gif, svg, webp.
- Редактор текста — WYSIWYG с таблицами, медиа, аккордеоном, исходным кодом и предпросмотром.
- Списки: вкладки-фильтры сверху, фильтр по колонкам, выбор числа записей (10/25/50/100),
  массовые действия по чекбоксам.

## Обязательная структура каждого модульного документа

```
# Lola LMS — ТЗ. <Номер>. <Название модуля>

## 1. Назначение и границы
## 2. Роли и скоупы (таблица: действие × роль)
## 3. Сущности и поля
     таблица: поле | тип | обяз. | значение по умолчанию | валидация | комментарий
## 4. Состояния и переходы (state machine словами или таблицей)
## 5. Экраны
     по каждому: состав, что видно каждой роли, пустое состояние, загрузка, ошибка
## 6. Формы
     полный перечень полей с типом контрола, подсказкой, валидацией и текстом ошибки
## 7. Правила и алгоритмы (нумерованные, проверяемые)
## 8. Уведомления (код, событие, канал, шаблон, кому)
## 9. Отчёты и выгрузки (колонки, фильтры)
## 10. API (метод, путь, вход, выход, ошибки)
## 11. Фоновые задачи
## 12. Крайние случаи
## 13. Критерии приёмки (Дано → Коли → Тоді)
## 14. Сверено с эталоном
## 15. Гипотезы и принятые по ним решения
```

## Правила письма

- Русский язык документа, украинские тексты интерфейса — в кавычках как есть.
- Никаких «и т.д.», «и прочее»: перечисления полные.
- Каждое правило формулируется проверяемо: «не больше 3 попыток за 15 минут», а не «ограничить».
- Тексты ошибок и подсказок писать сразу на украинском — они идут в i18n.
- Если требование выведено логически, а не снято с эталона, помечать `[решение]`.
- Если снять с эталона не удалось (модуль не используется, форма не открывается,
  экран требует изменения данных), **пустых мест не оставлять**: формулировать
  `[гипотеза]` — как это, вероятно, устроено, — и сразу за ней принятое решение
  для Lola с обоснованием. Гипотеза пишется так, чтобы её можно было опровергнуть
  одним взглядом на эталон, и помечается строкой «Чем проверяется».
- `[сверить]` остаётся только для того, что реально планируется досмотреть.
- Ничего не выдумывать про чужой код: эталон — источник требований, не реализации.
