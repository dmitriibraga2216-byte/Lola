# Lola LMS — ТЗ. 28. Рекрутинг: кандидаты и воронка

## 1. Назначение и границы

Модуль ведёт человека от отклика на вакансию до решения «нанять / отказать». Кандидат —
это человек, который **ещё не сотрудник**, но уже проходит контент Lola: тестовое задание,
психологический тест, авто-собеседование. Результаты этого прохождения — основание для
решения о найме, а при найме они переносятся вместе с человеком и не переснимаются.

**Входит в модуль:** реестр кандидатов, воронка (список и канбан), карточка кандидата,
оценки кандидата, комментарии рекрутера, приглашение на прохождение, найм и отказ,
архивация, перенос кандидата в сотрудники.

**Не входит:** вакансии и публикация на площадках — `docs/v2/29-vacancies.md`; авто-собеседование
и «3Д-резюме» — `docs/v2/30-ai-interview.md`; сам контент и правила прохождения — базовое ТЗ
(`docs/10-catalog-learning.md`, `docs/15-assignments.md`).

**Границы ответственности.** Модуль не заводит собственный механизм назначения контента и
собственные правила прохождения. Кандидату назначается тот же `assignments`, что и
сотруднику: попытки, проходной балл, лимит времени и сроки живут в назначении (инвариант 1).
Вакансия задаёт, **что** назначить кандидату, но не заменяет назначение.

**Зачем это Lola.** Первый тенант — сеть общественного питания с массовым наймом линейного
персонала и высокой текучестью. Воронка кандидатов, в которой человек до собеседования
проходит короткий тест на внимательность и смотрит вводное видео, экономит самый дорогой
ресурс — время управляющего точкой.

## 2. Роли и скоупы

Новые скоупы: `candidate.view`, `candidate.edit`, `candidate.assign`, `candidate.decide`,
`candidate.hire`, `candidate.delete`, `candidate.status.manage`.

| Действие | Кандидат | Рекрутер | Наставник | Керівник точки | HR / Админ | Оператор платформы |
|---|---|---|---|---|---|---|
| Видеть свой прогресс | ✓ | — | — | — | — | — |
| Видеть список кандидатов | — | ✓ своих + точек | — | ✓ своей точки | ✓ | — |
| Видеть карточку кандидата | — | ✓ | ✓ только назначенную ему проверку | ✓ своей точки | ✓ | — |
| Создавать кандидата | — | ✓ | — | ✓ | ✓ | — |
| Редактировать карточку | — | ✓ свои | — | — | ✓ | — |
| Назначать контент | — | ✓ | — | — | ✓ | — |
| Ставить ручную оценку | — | ✓ | ✓ по своим проверкам | ✓ | ✓ | — |
| Двигать по статусам | — | ✓ | — | ✓ | ✓ | — |
| Нанять / отказать | — | ✓ | — | — | ✓ | — |
| Редактировать справочник статусов | — | — | — | — | ✓ | — |
| Удалить кандидата (право на забвение) | — | — | — | — | ✓ | — |
| Видеть персональные данные (телефон, e-mail, резюме) | — | ✓ | — | ✓ маскировано | ✓ | — |

[решение] Наставник видит карточку кандидата **только** в объёме назначенной ему проверки:
ответ, критерии, история попыток. Контакты и резюме ему не показываются — он оценивает
работу, а не человека. Это снижает цену ошибки в правах на чувствительных данных.

[решение] Оператор платформы не имеет доступа к кандидатам ни в каком объёме, включая
impersonation: кандидат — самая чувствительная категория ПД в продукте (человек, который
не является клиентом тенанта и не подписывал с ним ничего, кроме согласия на обработку).

## 3. Сущности и поля

### 3.1 Связь кандидата и сотрудника — ключевое решение модуля

[решение] **Кандидат и сотрудник — один человек в одной таблице `users`, различающийся полем
`kind`.** Отдельная таблица `candidates` не заводится.

Обоснование:
1. Прохождение контента уже завязано на `users` через `assignments`, `enrollments`,
   `attempts`, `lesson_progress`, `media_assets.owner_user_id`. Вторая таблица людей
   потребовала бы либо дублировать всю эту цепочку, либо делать полиморфные ссылки —
   и то и другое ломает RLS и внешние ключи.
2. При найме история прохождения должна сохраниться без миграции строк. Смена `kind` —
   одно поле, ноль переносов.
3. На втором эталоне (Sintegrum) формы кандидата и сотрудника почти совпадают, а внутренний
   API сводит обе сущности к общему предку. Это подтверждает, что различие — в жизненном
   цикле, а не в природе объекта.

Риск и как он снимается: список сотрудников не должен показывать кандидатов и наоборот.
Поэтому `kind` — **обязательное поле с индексом**, а все существующие выборки людей в базовом
ТЗ получают явный фильтр (см. `docs/v2/39-patches.md`, П-16.1).

### 3.2 `alter table users`

```sql
alter table users
  add column kind               text not null default 'employee',
  add column candidate_state    text,
  add column candidate_status_id uuid,
  add column source             text,
  add column source_detail      text,
  add column vacancy_id         uuid,
  add column recruiter_id       uuid references users(id),
  add column access_until       date,
  add column comm_language      text not null default 'uk',
  add column resume_asset_id    uuid references media_assets(id),
  add column converted_from_candidate_at timestamptz,
  -- `hired_at date` уже объявлено в базовом ТЗ (`02` §2.3). Новую колонку не добавляем;
  -- если нужна точность до времени — меняем тип: alter column hired_at type timestamptz.
  add column consent_given_at   timestamptz,
  add column consent_expires_at date,
  add constraint users_kind_chk check (kind in ('employee','candidate')),
  add constraint users_candidate_state_chk
    check (candidate_state is null or candidate_state in ('active','hired','rejected','archived','withdrawn')),
  add constraint users_candidate_coherence_chk
    check ((kind = 'candidate' and candidate_state is not null)
        or (kind = 'employee'  and candidate_state is null));

create index idx_users_tenant_kind on users (tenant_id, kind);
create index idx_users_tenant_candidate_status on users (tenant_id, candidate_status_id)
  where kind = 'candidate';
create index idx_users_tenant_recruiter on users (tenant_id, recruiter_id)
  where kind = 'candidate';
create index idx_users_tenant_vacancy on users (tenant_id, vacancy_id)
  where kind = 'candidate';
```

| Поле | Тип | Обяз. | По умолчанию | Валидация | Комментарий |
|---|---|---|---|---|---|
| `kind` | text | да | `employee` | `employee` \| `candidate` | Природа записи. Меняется только при найме |
| `candidate_state` | text | для кандидата | — | 5 значений | Терминальное состояние воронки, см. §4 |
| `candidate_status_id` | uuid | нет | — | FK `candidate_statuses` | Колонка канбана. Отделено от `candidate_state` намеренно, см. §4.1 |
| `source` | text | нет | — | `manual` \| `vacancy_link` \| `job_board` \| `referral` \| `import` \| `api` | Откуда пришёл |
| `source_detail` | text | нет | — | ≤200 | Название площадки или ФИО рекомендателя |
| `vacancy_id` | uuid | нет | — | FK `vacancies` | Вакансия, на которую откликнулся |
| `recruiter_id` | uuid | нет | — | FK `users`, `kind='employee'` | Ответственный рекрутер |
| `access_until` | date | нет | — | ≥ сегодня при вводе | До какой даты кандидат может входить и проходить контент |
| `comm_language` | text | да | `uk` | код из включённых языков тенанта | Язык писем и интерфейса для кандидата |
| `resume_asset_id` | uuid | нет | — | FK `media_assets`, `origin='candidate_cv'` | Резюме (CV). Поле общее с сотрудником |
| `hired_at` | date | нет | — | — | **Уже есть в базовом ТЗ** (`02` §2.3). Не добавляется заново; при найме заполняется |
| `converted_from_candidate_at` | timestamptz | нет | — | — | Заполняется при смене `kind`; сохраняет факт, что сотрудник пришёл через воронку |
| `consent_given_at` | timestamptz | для кандидата | — | — | Согласие на обработку ПД, см. §7.9 |
| `consent_expires_at` | date | для кандидата | `consent_given_at + 6 мес.` | — | Дата, после которой ПД подлежат стиранию |

[решение] `access_until` — это **право входа**, а не дедлайн прохождения. Дедлайн живёт
в назначении (инвариант 1). Путать их нельзя: кандидат может иметь дедлайн по тесту
14 числа, а доступ к платформе — до 30-го, чтобы посмотреть результат.

### 3.3 `candidate_statuses` — справочник колонок воронки

```sql
create table candidate_statuses (
  id          uuid primary key default gen_random_uuid(),
  tenant_id   uuid not null references tenants(id) on delete cascade,
  code        text not null,
  name_uk     text not null,
  name_en     text,
  color       text not null default 'ink',
  sort        int  not null,
  is_system   boolean not null default false,
  maps_to     text not null default 'active',
  is_active   boolean not null default true,
  created_at  timestamptz not null default now(),
  created_by  uuid references users(id),
  constraint candidate_statuses_maps_to_chk
    check (maps_to in ('active','hired','rejected','archived','withdrawn')),
  constraint candidate_statuses_color_chk
    check (color in ('ink','sun','teal','coral')),
  unique (tenant_id, code)
);
create index idx_candidate_statuses_tenant on candidate_statuses (tenant_id, sort);
```

Системные статусы, создаются при инициализации тенанта (`is_system = true`, код неизменяем):

| `code` | `name_uk` | `maps_to` | `color` | Смысл |
|---|---|---|---|---|
| `new` | «Не розпочали» | active | ink | Заведён, но ещё ничего не проходил |
| `in_progress` | «Проходять» | active | teal | Идёт по назначенному контенту |
| `on_review` | «На перевірці» | active | sun | Ждёт человека: проверку задания или решение |
| `approved` | «Схвалені» | active | teal | Прошёл, рекомендован к найму |
| `doubt` | «Під сумнівом» | active | sun | Решение отложено |
| `rejected` | «Відхилені» | rejected | coral | Отказ |

[решение] Справочник **расширяемый**: администратор добавляет свои колонки (на эталоне это
служебная колонка «Додати» в канбане). Но каждая пользовательская колонка обязана указать
`maps_to` — к какому из пяти терминальных состояний она приравнивается. Иначе отчётность
по воронке разваливается, как только тенант заведёт «Передзвонити у січні».

[решение] Системные статусы нельзя удалить и нельзя переименовать `code`; `name_uk`, `color`
и `sort` — можно. Удаление пользовательского статуса, в котором есть кандидаты, запрещено:
`409 candidate_status.in_use` со списком и предложением перенести.

### 3.4 `candidate_scores` — оценки кандидата

```sql
create table candidate_scores (
  id            uuid primary key default gen_random_uuid(),
  tenant_id     uuid not null references tenants(id) on delete cascade,
  candidate_id  uuid not null references users(id) on delete cascade,
  kind          text not null,
  value_num     numeric(6,2),
  scale_id      uuid references scales(id),
  scale_level_id uuid references scale_levels(id),
  comment       text,
  source_type   text,
  source_id     uuid,
  author_id     uuid references users(id),
  is_current    boolean not null default true,
  created_at    timestamptz not null default now(),
  constraint candidate_scores_kind_chk
    check (kind in ('manual','task','ai','recruiter')),
  constraint candidate_scores_value_chk
    check (value_num is not null or scale_level_id is not null)
);
create index idx_candidate_scores_tenant on candidate_scores (tenant_id, candidate_id, kind);
create unique index uq_candidate_scores_current
  on candidate_scores (tenant_id, candidate_id, kind) where is_current;
```

[решение] **Четыре независимых вида оценки, не сводимые в один `score`.** На эталоне их три
(`Оцінка`, `Оцінка ТЗ`, `Оцінка ШІ`), плюс в настройках фигурирует четвёртая — «Оцінка
рекрутера». Разделяем все четыре:

| `kind` | Кто ставит | Источник | Смысл |
|---|---|---|---|
| `manual` | человек | вручную в карточке | Общее впечатление |
| `task` | наставник/рекрутер | проверка практикума или теста | Качество тестового задания |
| `ai` | система | авто-собеседование, `docs/30` | Оценка ответов моделью |
| `recruiter` | рекрутер | итоговое решение | Рекомендация к найму |

Сведение в единое число запрещено на уровне модели: разные оценки отвечают на разные
вопросы, а усреднение прячет случай «блестящее тестовое, провальное собеседование», ради
которого воронка и существует.

[решение] История оценок сохраняется: новая оценка того же вида создаёт новую строку и
снимает `is_current` с предыдущей. Переоценка кандидата — обычное дело, а её след нужен
при разборе решения.

### 3.5 `candidate_comments`

```sql
create table candidate_comments (
  id           uuid primary key default gen_random_uuid(),
  tenant_id    uuid not null references tenants(id) on delete cascade,
  candidate_id uuid not null references users(id) on delete cascade,
  author_id    uuid not null references users(id),
  body         text not null,
  visibility   text not null default 'recruiters',
  created_at   timestamptz not null default now(),
  edited_at    timestamptz,
  deleted_at   timestamptz,
  constraint candidate_comments_visibility_chk
    check (visibility in ('recruiters','managers','all_staff')),
  constraint candidate_comments_body_chk check (length(body) between 1 and 4000)
);
create index idx_candidate_comments_tenant on candidate_comments (tenant_id, candidate_id, created_at desc);
```

[решение] Комментарии никогда не видны самому кандидату — ни при какой `visibility`. Это
служебная переписка о человеке; кандидат получает только формальные уведомления.

### 3.7 Что НЕ заводим

- Отдельную таблицу назначений для кандидата — используется `assignments` (инвариант 1).
- Отдельную таблицу прогресса — `enrollments`, `attempts`, `lesson_progress`.
- Отдельное хранилище файлов — `media_assets` с `origin = 'candidate_cv'`
  (см. `docs/v2/34-storage.md`).

## 4. Состояния и переходы

### 4.1 Две независимые оси

[решение] У кандидата **две оси состояния, и их нельзя сливать**:

1. `candidate_state` — терминальное состояние воронки, закрытый перечень из пяти значений,
   код продукта опирается только на него.
2. `candidate_status_id` — колонка канбана, расширяемый справочник тенанта, нужен людям.

Каждая колонка знает, к какому состоянию она приравнивается (`maps_to`). Отчётность,
лимиты тарифа и уведомления смотрят на ось 1; интерфейс — на ось 2. Без такого разделения
первая же пользовательская колонка ломает все отчёты — это самая частая ошибка в системах
с настраиваемыми статусами.

### 4.2 Переходы `candidate_state`

```
active ──hire──────────→ hired      (kind меняется на employee, §7.6)
active ──reject────────→ rejected   (обязательна причина)
active ──archive───────→ archived   (авто по правилу или вручную)
active ──withdraw──────→ withdrawn  (кандидат сам отказался)
rejected ──reopen──────→ active     (только admin, с причиной, не позднее 12 мес.)
archived ──reopen──────→ active     (только admin, если не истёк consent)
hired   ── нет переходов назад
withdrawn ──reopen─────→ active
```

| Из | В | Кто | Условие | Последствие |
|---|---|---|---|---|
| `active` | `hired` | `candidate.hire` | заполнены точка, должность, дата выхода | `kind='employee'`, освобождается лимит кандидатов, занимается лимит сотрудников |
| `active` | `rejected` | `candidate.decide` | указана причина из справочника | уведомление кандидату (если включено), запуск таймера авто-архивации |
| `active` | `archived` | авто / `candidate.decide` | нет активности N дней либо ручное решение | доступ кандидата закрывается |
| `active` | `withdrawn` | `candidate.edit` или сам кандидат | — | доступ закрывается |
| `rejected` | `active` | `admin` | `consent_expires_at` не истёк | восстанавливается доступ, пишется в `audit_log` |
| `hired` | любое | — | — | **запрещено**: сотрудник увольняется через офбординг (`docs/33`), а не возвратом в воронку |

[решение] Найм необратим в рамках модуля. Ошибочный найм исправляется не откатом, а
увольнением с пометкой причины — иначе в системе появляется человек с `kind='employee'`
и живым прогрессом, которого «вернули в кандидаты», и все отчёты по штату начинают врать.

### 4.3 Автоматические переходы статуса канбана

| Событие | Переход | Условие |
|---|---|---|
| Кандидат начал первый элемент назначения | `new` → `in_progress` | статус всё ещё `new` |
| Все назначения завершены, есть ручная проверка в очереди | `in_progress` → `on_review` | — |
| Все назначения завершены, ручной проверки нет | `in_progress` → `on_review` | ждёт решения человека |
| Провалена последняя попытка обязательного теста | без перехода | [решение] система **не отказывает автоматически**, см. §7.4 |

## 5. Экраны

### 5.1 Список кандидатов — `/candidates`

Шапка: «Кандидати», справа счётчик «Кандидатів: N із M» (M — лимит тарифа, см. `docs/35`).

Фильтры: поиск по ФИО/телефону/e-mail; точка; вакансия; курс; статус (мультивыбор,
по умолчанию — все колонки с `maps_to='active'`); рекрутер; источник; период добавления.
Переключатель вида: список / канбан.

Колонки: чекбокс · Прізвище Ім'я · Контакти · Точка · Вакансія · Курс і прогрес ·
Доданий · Останній вхід · Оцінка · Оцінка ТЗ · Оцінка ШІ · Статус · «⋮».

Массовые действия по чекбоксам: назначить контент, сменить статус, назначить рекрутера,
экспорт, архивировать. Каждое — с подтверждением и указанием числа записей.

Пустое состояние: «Кандидатів ще немає» + «Додати кандидата» + ссылка «Як налаштувати
воронку». Загрузка — скелет из 8 строк. Ошибка — «Не вдалося завантажити список» + «Оновити».

Роли: рекрутер видит своих и точек, где он назначен; керівник точки — только свою точку,
контакты маскированы (`+380** *** ** 67`); HR и админ — всех.

### 5.2 Канбан — `/candidates?view=board`

Колонки = активные `candidate_statuses` по `sort`. Карточка: ФИО, вакансия, точка, три
оценки компактно, индикатор прогресса, дней в текущем статусе, аватар рекрутера, флажок
просроченного `access_until`. Перетаскивание карточки меняет статус и пишет в
`candidate_status_history`. Справа — колонка «+ Додати статус» для `candidate.status.manage`.

[решение] Колонка с числом карточек больше 200 не грузит их все: показывает первые 50 и
кнопку «Показати ще». Канбан на массовом найме — первое место, где страница умирает.

### 5.3 Карточка кандидата — `/candidates/:id`

Шапка: ФИО, статус (меняется селектом), вакансия, рекрутер, кнопки «Найняти», «Відхилити»,
«⋮» (архивировать, назначить контент, скопировать ссылку для входа, видалити).

Вкладки:
1. **Огляд** — контакты, резюме (просмотр и скачивание), источник, дата добавления,
   `access_until` со светофором, четыре оценки с авторами и датами, последние 5 событий.
2. **Проходження** — назначения со статусами из пяти канонических, прогресс, попытки,
   ссылки на результаты, «Час на контент» и «Час на випробування» (см. `docs/37`).
3. **Співбесіда** — результат авто-собеседования и «3Д-резюме» (`docs/30`); вкладки нет,
   если собеседование не назначалось.
4. **Коментарі** — тред, видимость по `visibility`.
5. **Історія** — полная лента: смены статуса, оценки, назначения, входы, отправленные письма.

Пустое состояние вкладки «Проходження»: «Кандидату ще нічого не призначено» + кнопка.

### 5.4 Настройка воронки — `/settings/candidate-statuses`

Список статусов с drag-сортировкой, цвет, `maps_to`, признак системного, счётчик кандидатов
в статусе. Для `candidate.status.manage`.

## 7. Правила и алгоритмы

1. **Лимит кандидатов.** В лимит тарифа считаются кандидаты с `candidate_state='active'`.
   `hired`, `rejected`, `archived`, `withdrawn` не считаются. Проверка — в момент создания
   и в момент `reopen`; при превышении `409 limit.candidates_exceeded` (см. `docs/35`).
2. **Уникальность человека.** Перед созданием ищется совпадение по телефону и e-mail среди
   всех `users` тенанта. Найдено — форма показывает карточку найденного («Такий кандидат
   уже є: <ФИО>, статус <…>, доданий <дата>») и предлагает открыть её или создать повторно
   с явным подтверждением. Тихого дубликата быть не должно: повторный отклик того же
   человека — норма, а два профиля с разной историей — источник неверных решений.
3. **Повторный отклик ранее отказанного.** Если найден кандидат в `rejected` с отказом
   позднее чем 6 месяцев назад, показывается предупреждение с датой и причиной прошлого
   отказа. Блокировки нет — решение за человеком.
4. **Провал теста не равен отказу.** Система никогда не переводит кандидата в `rejected`
   автоматически. Провал обязательного назначения ставит статус `on_review` и уведомляет
   рекрутера. Обоснование: автоматический отказ по формальному результату — это дорогая
   ошибка (человек мог провалить тест из-за интерфейса на телефоне), и юридически это
   автоматизированное решение, требующее возможности обжалования.
5. **Авто-архивация отказанных.** Если в настройках тенанта включено «Автоматично
   архівувати відхилених» с периодом N дней (по умолчанию 30, диапазон 7–365), фоновая
   задача переводит `rejected` → `archived` по истечении N дней с момента отказа. Архивация
   закрывает доступ кандидата, но не стирает данные — стирание делает отдельное правило 9.
6. **Найм.** Транзакционно: `kind='employee'`; `candidate_state='hired'`; `hired_at=current_date`;
   `converted_from_candidate_at=now()`; `candidate_status_id=null`; создаётся
   `user_placements` по выбранной точке и должности; назначаются курсы онбординга;
   пересчитываются оба лимита; пишется `audit_log` с кодом `candidate.hired`.
   Вся история прохождения остаётся на том же `user_id` и становится историей сотрудника.
   При ошибке на любом шаге — полный откат, кандидат остаётся кандидатом.
7. **Доступ кандидата.** Кандидат входит по тому же OTP, что и сотрудник. Вход запрещён,
   если `candidate_state != 'active'` или `access_until < сегодня`. Текст отказа:
   «Термін доступу завершився. Зверніться до рекрутера.» — без раскрытия причины отказа
   по существу.
8. **Видимость контента.** Кандидату доступны только те курсы, которые ему назначены явно.
   Каталог, база знаний, корпоративный хаб, новости и любые данные о сотрудниках для
   `kind='candidate'` закрыты на уровне API, а не только меню.
9. **Согласие и стирание ПД.** `consent_expires_at` по умолчанию `consent_given_at + 6 мес.`,
   настраивается тенантом в диапазоне 1–24 мес. Ежедневная задача находит кандидатов, у
   которых срок истёк и состояние не `hired`, и обезличивает запись: ФИО → «Кандидат
   №<короткий id>», телефон, e-mail, резюме и комментарии удаляются, прохождение и оценки
   остаются в обезличенном виде для статистики. Операция необратима и пишется в `audit_log`.
   За 14 дней до стирания рекрутер получает уведомление со списком.
10. **Маскирование контактов.** Роли без `candidate.view` в полном объёме видят телефон как
    `+380** *** ** 67` и e-mail как `a****@gmail.com`. Маскирование делается на сервере.
11. **Счёт времени в статусе.** «Днів у статусі» считается от последней записи в
    `candidate_status_history`, а не от даты создания.
12. **Ограничение частоты приглашений.** Повторное приглашение одному кандидату — не чаще
    раза в 24 часа и не более 5 раз всего.

## 9. Отчёты и выгрузки

1. **Воронка.** Колонки: статус, кандидатов, доля от вошедших, среднее время в статусе,
   конверсия в следующий. Фильтры: период, вакансия, точка, рекрутер, источник.
2. **Эффективность рекрутера.** Рекрутер · добавлено · проходят · на проверке · нанято ·

3. **Источники.** Источник · кандидатов · дошло до финала · нанято · стоимость найма
   (если в вакансии указан бюджет площадки, `docs/29`).
4. **Время до найма.** Медиана и 90-й перцентиль от создания до `hired`, в разрезе вакансий
   и точек.
5. **Отказы по причинам.** Причина · число · доля · разрез по вакансиям.
6. **Выгрузка кандидатов.** Все поля карточки, кроме резюме; оценки отдельными колонками.
   Выгрузка с контактами требует `candidate.view` в полном объёме и пишется в `audit_log`
   с числом строк — выгрузка базы кандидатов конкурентам является реальным риском.

## 12. Крайние случаи

1. **Телефон кандидата совпадает с телефоном действующего сотрудника.** Создание
   блокируется: `409 candidate.is_employee` с текстом «Ця людина вже працює у компанії».
2. **Кандидат нанят, но не вышел.** Назад в воронку нельзя (§4.2). Порядок: уволить через
   офбординг с причиной «Не вийшов», при желании создать нового кандидата; связь между
   записями фиксируется комментарием.
3. **Вакансия закрыта, кандидаты в процессе.** Прохождение не прерывается. Рекрутер получает
   список «N кандидатів проходять відбір на закриту вакансію» и решает по каждому.
4. **Удалён рекрутер.** `recruiter_id` не обнуляется; кандидаты попадают в фильтр
   «Без відповідального» и в еженедельный дайджест HR.
5. **Кандидат прошёл, но лимит сотрудников исчерпан.** Найм блокируется с указанием, сколько
   мест не хватает и куда идти; кандидат остаётся `approved`, доступ продлевается
   автоматически на 14 дней, чтобы не потерять человека из-за биллинга.
6. **Два рекрутера одновременно двигают карточку.** Оптимистическая блокировка по
   `updated_at`; проигравший получает `409 conflict` и актуальное состояние.
7. **Кандидат отозвал согласие на обработку ПД.** Немедленное обезличивание по правилу 9
   независимо от `consent_expires_at`, доступ закрывается, рекрутер уведомляется.
8. **`access_until` истёк посреди попытки теста.** Начатая попытка доводится до конца
   (доступ проверяется на входе, а не на каждом запросе), новые не начинаются.
9. **Импорт кандидатов превышает лимит.** Импорт не выполняется частично: если строк больше,
   чем свободных мест, задача завершается ошибкой со списком и ничего не создаёт.
10. **Кандидат подал повторный отклик через площадку, пока первый в работе.** Создаётся не
    новый профиль, а событие в истории существующего: «Повторний відгук <дата>, джерело <…>».

## 13. Критерии приёмки

1. **Дано** тенант с лимитом 100 кандидатов и 100 активными, **коли** рекрутер создаёт
   101-го, **тоді** ответ `409 limit.candidates_exceeded`, кандидат не создан, счётчик
   не изменился.
2. **Дано** кандидат с телефоном X, **коли** создаётся второй с тем же телефоном,
   **тоді** форма показывает карточку существующего и требует явного подтверждения;
   без подтверждения запись не создаётся.
3. **Дано** кандидат провалил последнюю попытку обязательного теста, **коли** попытка
   закрыта, **тоді** `candidate_state` остаётся `active`, статус — `on_review`,
   рекрутеру уходит уведомление, отказ автоматически не ставится.
4. **Дано** кандидат в статусе `approved` с пройденным курсом и двумя оценками, **коли**
   рекрутер нажимает «Найняти» и заполняет точку, должность и дату, **тоді** `kind` = `employee`,
   прогресс и оценки остаются на том же `user_id`, лимит кандидатов уменьшился на 1,
   лимит сотрудников увеличился на 1, в `audit_log` есть `candidate.hired`.
5. **Дано** тенант завёл пользовательский статус «Передзвонити» с `maps_to='active'`,
   **коли** строится отчёт по воронке, **тоді** кандидаты этого статуса учтены как активные,
   а не выпадают из отчёта.
6. **Дано** пользовательский статус, в котором 3 кандидата, **коли** админ его удаляет,
   **тоді** `409 candidate_status.in_use` со списком трёх.
7. **Дано** кандидат отказан 31 день назад при настройке авто-архивации 30 дней, **коли**
   отработала `candidate.auto_archive`, **тоді** состояние `archived`, вход кандидата
   возвращает «Термін доступу завершився».
8. **Дано** кандидат с истёкшим согласием, **коли** отработала `candidate.consent_sweep`,
   **тоді** ФИО, телефон, e-mail, резюме и комментарии удалены, прохождение и оценки
   сохранены, запись в `audit_log` есть, операция не откатывается.
9. **Дано** керівник точки, **коли** он открывает карточку кандидата другой точки,
   **тоді** `404`, а не `403`.
10. **Дано** наставник с назначенной проверкой, **коли** он открывает карточку кандидата,
    **тоді** видит ответ и критерии, не видит телефон, e-mail и резюме.
11. **Дано** кандидат в статусе `hired`, **коли** делается попытка перевести его в `active`,
    **тоді** `409`, состояние не меняется.
12. **Дано** 250 кандидатов в одной колонке канбана, **коли** открывается доска, **тоді**
    загружаются первые 50 и кнопка «Показати ще», время ответа API ≤ 400 мс.

## 14. Сверено с эталоном

Снято с Sintegrum (`/candidates`, форма создания, канбан, `/recruiters`, `/company-settings`):
- Шесть статусных колонок канбана и служебная колонка добавления собственной — §3.3.
- Три независимых числовых оценки в списке; четвёртая («Оцінка рекрутера») — из условия
  авто-отправки 3Д-резюме в настройках компании — §3.4.
- Состав формы создания: имя, фамилия, e-mail, телефон с кодом страны по умолчанию,
  резюме файлом, обязательная точка, язык писем кандидату, «Доступ до» с пояснением,
  счётчик назначенных материалов — §6.1.
- Колонки списка кандидатов — §5.1.
- Счётчики «Найняті» и «Архівні» в статистике рекрутёров — легли в `candidate_state` §4.2.
- Раздельный лимит тарифа по кандидатам — §7.1, детально `docs/35`.
- Авто-архивация отклонённых через N дней из настроек компании — §7.5.

Не снималось с эталона и является решением Lola: разделение осей `candidate_state` и
`candidate_status_id`; единая таблица `users` с полем `kind`; запрет автоматического отказа;
модель согласия и стирания ПД; маскирование контактов; правила дублирования.

## 15. Гипотезы и принятые по ним решения

**Г-28.1. Содержимое карточки кандидата на эталоне.** Снять не удалось: в эталонной
инсталляции ноль кандидатов, открыть нечего, а создавать запрещено правилом read-only.
[гипотеза] Карточка содержит историю прохождения, результаты оценок, резюме, комментарии
рекрутера и ссылку на 3Д-резюме.
[решение] Состав карточки спроектирован от задачи принятия решения о найме: пять вкладок
§5.3, где «Огляд» отвечает на вопрос «брать или нет» без переходов.
*Чем проверяется:* завести на эталоне тестового кандидата, провести по канбану, открыть
карточку и сверить состав вкладок.

**Г-28.2. Смысл поля «Доступ до».** Тултип на эталоне не раскрывался.
[гипотеза] Это дата, после которой кандидат теряет доступ к платформе.
[решение] Трактуем как право входа, отдельно от дедлайна назначения (§3.2), и пишем
пояснение текстом в форме, а не иконкой.
*Чем проверяется:* навести курсор на ⓘ у поля на эталоне и прочитать текст.

**Г-28.3. Статусы «Найняті» и «Архівні».** В канбане их нет, в статистике рекрутёров —
есть как счётчики.
[гипотеза] Это терминальные состояния поверх канбана, а не колонки.
[решение] Именно так и сделано: ось `candidate_state` (§4.1), отдельная от колонок.
*Чем проверяется:* довести кандидата до «Схвалені» и посмотреть, появляется ли действие
«Найняти» и исчезает ли он с доски.

**Г-28.4. Системные статусы: можно ли переименовать и удалить.**
[гипотеза] Шесть исходных колонок защищены от удаления.
[решение] `is_system` запрещает удаление и смену `code`, разрешает смену названия, цвета
и порядка (§3.3).
*Чем проверяется:* попытаться удалить колонку «Проходять» на эталоне.

**Г-28.5. Содержимое меню «⋮» в списке кандидатов.** Не раскрывалось.
[гипотеза] Массовые действия и экспорт.
[решение] Состав массовых действий определён самостоятельно (§5.1) исходя из сценариев
массового найма.
*Чем проверяется:* открыть меню на эталоне.

**Г-28.6. Как выглядит карточка в канбане.** Нет данных на эталоне.
[решение] Состав карточки определён от задачи: что должно быть видно, чтобы двигать
карточку не открывая (§5.2).
*Чем проверяется:* создать кандидата и посмотреть доску.

**Г-28.7. Считает ли эталон кандидатов в лимит по всем состояниям или только по активным.**
Снять точно не удалось: в инсталляции ноль кандидатов при лимите 100.
[гипотеза] По активным, иначе лимит исчерпался бы историей.
[решение] Считаем только `active` (§7.1). Если окажется иначе — это решение всё равно
предпочтительнее: тенант не должен платить за архив.
*Чем проверяется:* создать кандидата, отказать, посмотреть, уменьшился ли счётчик «із 100».
