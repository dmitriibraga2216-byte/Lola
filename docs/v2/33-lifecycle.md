# Lola LMS — ТЗ. 33. Этапы жизненного цикла сотрудника и возможности контента

## 1. Назначение и границы

Документ решает главное архитектурное расхождение между двумя эталонами и задаёт рамку,
в которую встают все остальные документы этого пакета.

**Суть расхождения.** Первый эталон (LMS Collaborator) строит продукт вокруг **свободного
каталога курсов** с пользовательскими категориями и программами/траекториями поверх. Второй
эталон (Sintegrum) строит его вокруг **десяти фиксированных категорий жизненного цикла**
(рекрутинг → онбординг → интеграция → повышение квалификации → аттестация → психологические
тесты → база знаний → офбординг → библиотека → отчёт об ошибках), причём у каждой категории
**своё поведение**: у «Бази знань» нет ни графа, ни прогресса, ни дедлайна — только плоский
список назначенных документов; у «Психологічних тестів» нет ИИ-генерации; «Звіт про помилки»
вообще не список курсов, а очередь обращений.

Две модели не складываются автоматически: в первой категория — это ярлык каталога, во второй —
ветка продуктовой логики.

**Что входит в документ:** принятое решение по этому расхождению; перечень этапов жизненного
цикла; модель возможностей контента (`capabilities`); офбординг как этап; правила перехода
человека между этапами; влияние на навигацию, отчётность и назначения.

**Что не входит:** сам контент и его типы — базовое ТЗ (`docs/11-content-lessons.md`);
рекрутинговый этап целиком — `docs/v2/28-recruiting-candidates.md`, `docs/v2/29-vacancies.md`,
`docs/v2/30-ai-interview.md`; библиотека переиспользуемого контента — `docs/v2/31-module-library.md`;
очередь обращений по контенту — `docs/v2/36-content-feedback.md`.

## 2. Роли и скоупы

Новые скоупы: `lifecycle.view`, `lifecycle.manage` (редактирование перечня этапов тенанта),
`offboarding.start`, `offboarding.complete`.

| Действие | Сотрудник | Наставник | Керівник точки | HR / Админ | Оператор платформы |
|---|---|---|---|---|---|
| Видеть своё обучение, сгруппированное по этапам | ✓ | ✓ | ✓ | ✓ | — |
| Видеть этап другого человека | — | ✓ своих подопечных | ✓ своей точки | ✓ | — |
| Присваивать курсу этап | — | — | — | ✓ | — |
| Включать и выключать этапы тенанта | — | — | — | ✓ | — |
| Менять набор возможностей этапа | — | — | — | — | ✓ |
| Запустить офбординг | — | — | ✓ своей точки | ✓ | — |
| Завершить офбординг | — | — | — | ✓ | — |

[решение] Набор возможностей этапа (`capabilities`, §3.3) меняет только оператор платформы,
а не администратор тенанта. Возможности — это про то, какой код выполняется; отдавать их
тенанту означает позволить ему сломать продукт настройкой. Тенант включает и выключает
этапы, но не переопределяет их природу.

## 3. Сущности и поля

### 3.1 Принятое решение по расхождению

[решение] **Гибрид: свободный каталог остаётся основой, этап жизненного цикла — необязательный
атрибут курса, разное поведение выражается флагами возможностей, а не ветками кода.**

Формально:
1. `courses` сохраняет существующие `course_categories` (свободный справочник каталога) —
   ничего из базового ТЗ не ломается.
2. К курсу добавляется **необязательная** ссылка на `lifecycle_stages` — этап, к которому
   курс относится. Курс без этапа — нормальный курс каталога.
3. Поведение продукта определяется **не названием этапа**, а набором булевых возможностей
   (`capabilities`), объявленных у этапа. Код спрашивает «можно ли здесь считать прогресс»,
   а не «это база знаний или нет».
4. Перечень этапов — справочник платформы с фиксированными кодами; тенант включает нужные
   и переименовывает под себя, но не выдумывает новые коды.

**Почему так, а не калькой второго эталона.** Десять веток кода по названию категории — это
десять мест, где нужно не забыть новую категорию, и релиз на каждую. Уже на эталоне видно,
к чему это приводит: «Бібліотека модулів» и «Звіт про помилки» попали в меню «Треки», хотя
не являются ни треками, ни категориями — просто им не нашлось другого места. Флаги
возможностей дают ту же разницу в поведении, но проверяются в одном месте и расширяются
данными, а не кодом.

**Почему не чистым каталогом, как в базовом ТЗ.** Потому что разница в поведении реальна и
нужна: назначить человеку должностную инструкцию для ознакомления и назначить ему аттестацию —
это разные вещи. Без явного этапа они выглядят одинаково и в карточке человека, и в отчёте,
а руководитель точки должен видеть «трое на онбординге, один на аттестации», а не «четверо
проходят курсы».

**Цена решения, которую принимаем осознанно.** Этап не выводится из курса автоматически,
его надо проставить. Митигация — правило 7.2: курс, созданный из шаблона этапа или назначенный
правилом автоматизации, получает этап автоматически; массовая простановка делается фильтром
в каталоге.

### 3.2 `lifecycle_stages`

```sql
create table lifecycle_stages (
  id            uuid primary key default gen_random_uuid(),
  tenant_id     uuid not null references tenants(id) on delete cascade,
  code          text not null,
  name_uk       text not null,
  name_en       text,
  icon          text,
  color         text not null default 'ink',
  sort          int  not null,
  is_enabled    boolean not null default true,
  capabilities  jsonb not null default '{}'::jsonb,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now(),
  constraint lifecycle_stages_code_chk check (code in (
    'recruiting','onboarding','integration','training',
    'attestation','psychological','knowledge','offboarding')),
  constraint lifecycle_stages_color_chk check (color in ('ink','sun','teal','coral')),
  unique (tenant_id, code)
);
create index idx_lifecycle_stages_tenant on lifecycle_stages (tenant_id, sort);
```

[решение] Восемь кодов, а не десять. «Бібліотека модулів» и «Звіт про помилки» со второго
эталона — **не этапы**, а самостоятельные модули: первый описан в `docs/v2/31-module-library.md`,
второй в `docs/v2/36-content-feedback.md`. Их попадание в список категорий на эталоне — следствие
того, что у продукта одно меню на всё, и повторять это не нужно.

Справочник создаётся при инициализации тенанта. `code` неизменяем; `name_uk`, `icon`, `color`,
`sort`, `is_enabled`, `expected_days` — редактируются тенантом.

> [дополнено фазой 1, `44` В-3] Перечень кодов — **платформенный** и регистрируется в
> `docs/02-data-model.md` §«Перечисления» как `lifecycle_stage_code` (CLAUDE.md п. 13), рядом
> с `MEDIA_ORIGINS`, `QUIZ_KINDS` и `JOURNAL_SUBJECT_TYPES`. Тенант включает, переименовывает
> и сортирует этапы; выдумать код не может. Это же условие В-10: ключи разбивки хранилища
> сравнимы между тенантами только пока перечень платформенный.

### 3.3 Возможности этапа (`capabilities`)

Ключи объявлены платформой, значения — булевы. Перечень **фиксированный**: неизвестный ключ
отвергается `422 validation_failed`; отсутствующий ключ читается как `false`.

> [исправлено фазой 1, `44` В-3] Ранее: «Неизвестный ключ игнорируется». Тихое игнорирование —
> ошибка того же класса, что забытый фильтр по `kind`: опечатка `certificat` вместо
> `certificate` даёт выключенную возможность без единого признака, и обнаруживается тем, что
> человеку не выдали сертификат. Перечень объявлен как `STAGE_CAPABILITIES` в `shared/enums.ts`,
> проверяется zod при записи и констрейнтом `lifecycle_stages_capabilities_keys_check` в БД.

| Ключ | Смысл | Что ломается, если выключить |
|---|---|---|
| `progress` | считается ли процент прохождения | карточка показывает факт назначения, а не % |
| `deadline` | можно ли задать срок в назначении | поле срока скрыто в форме назначения |
| `grading` | выставляется ли оценка | нет баллов, нет «пройдено/провалено» |
| `attempts` | ограничивается ли число попыток | поле попыток скрыто |
| `review` | попадает ли работа в очередь проверки | элементы не появляются в `docs/37` |
| `certificate` | выдаётся ли сертификат | блок сертификата скрыт |
| `graph` | доступен ли граф-конструктор с ветвлением | только линейный состав |
| `ai_generate` | разрешена ли ИИ-генерация контента | кнопка генерации скрыта |
| `applies_to_candidate` | можно ли назначать кандидату | этап не виден в форме назначения кандидату |
| `applies_to_employee` | можно ли назначать сотруднику | то же для сотрудника |
| `counts_in_rating` | учитывается ли в рейтинге (`docs/38`) | назначения этапа не влияют на рейтинг |

Значения по умолчанию, создаваемые при инициализации тенанта:

| `code` | `name_uk` | progress | deadline | grading | attempts | review | certificate | graph | ai_generate | candidate | employee | rating |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| `recruiting` | «Рекрутинг» | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | ✓ | — | — |
| `onboarding` | «Онбординг» | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ |
| `integration` | «Інтеграція» | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | — | ✓ | ✓ |
| `training` | «Підвищення кваліфікації» | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ |
| `attestation` | «Атестація» | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | — | ✓ | ✓ |
| `psychological` | «Психологічні тести» | ✓ | ✓ | — | — | — | — | — | — | ✓ | ✓ | — |
| `knowledge` | «База знань» | — | — | — | — | — | — | — | ✓ | — | ✓ | — |
| `offboarding` | «Офбординг» | ✓ | ✓ | — | — | ✓ | — | ✓ | — | — | ✓ | — |

Обоснование неочевидных значений:
- **`knowledge`** — почти всё выключено. Это подтверждено эталоном: в карточке сотрудника
  назначенные документы базы знаний показаны плоским списком с одной датой назначения, без
  процента, дедлайна и времени. База знаний — это «ознакомься», а не «сдай».
- **`psychological`: `grading = false`.** Психометрическая методика даёт профиль, а не балл
  «сдал/не сдал». Оценивать человека по результату опросника выгорания — прямой вред;
  продукт не должен давать такую возможность технически.
- **`psychological`: `counts_in_rating = false`.** По той же причине: результат
  психологического теста не должен влиять на рейтинг сотрудника.
- **`attestation`: `ai_generate = false`.** Содержание аттестации — зона ответственности
  методиста; сгенерированная аттестация, по которой принимают кадровые решения, — риск,
  который мы не берём.
- **`offboarding`: `grading = false`, `attempts = false`.** Уходящего человека не оценивают.
  Офбординг — это передача дел и выходное интервью, а не экзамен.

### 3.4 `alter table courses`

```sql
alter table courses
  add column lifecycle_stage_id uuid references lifecycle_stages(id),
  add column stage_locked        boolean not null default false;

create index idx_courses_tenant_stage on courses (tenant_id, lifecycle_stage_id);
```

`stage_locked = true` запрещает смену этапа у курса, по которому уже есть завершённые
прохождения (см. правило 7.4).

### 3.5 `employee_lifecycle_state` — где человек находится сейчас

```sql
create table employee_lifecycle_state (
  id            uuid primary key default gen_random_uuid(),
  tenant_id     uuid not null references tenants(id) on delete cascade,
  user_id       uuid not null references users(id) on delete cascade,
  stage_id      uuid not null references lifecycle_stages(id),
  entered_at    timestamptz not null default now(),
  left_at       timestamptz,
  entered_by    uuid references users(id),
  reason_code   text,
  is_current    boolean not null default true,
  created_at    timestamptz not null default now()
);
create index idx_employee_lifecycle_state_tenant
  on employee_lifecycle_state (tenant_id, user_id, entered_at desc);
create unique index uq_employee_lifecycle_current
  on employee_lifecycle_state (tenant_id, user_id) where is_current;
```

[решение] Этап человека и этап курса — **разные вещи**, и их нельзя выводить друг из друга.
Человек «на онбординге» может параллельно проходить курс этапа «база знаний»; сотрудник,
давно работающий, может проходить онбординг-курс новой точки после перевода. Поэтому состояние
человека хранится явно, а не вычисляется из его назначений.

### 3.6 `offboarding_cases` — процесс увольнения

```sql
create table offboarding_cases (
  id               uuid primary key default gen_random_uuid(),
  tenant_id        uuid not null references tenants(id) on delete cascade,
  user_id          uuid not null references users(id) on delete cascade,
  state            text not null default 'started',
  reason_code      text not null,
  reason_text      text,
  last_working_day date not null,
  initiated_by     uuid references users(id),
  exit_interview_enrollment_id uuid references enrollments(id),
  handover_done_at timestamptz,
  access_revoked_at timestamptz,
  completed_at     timestamptz,
  created_at       timestamptz not null default now(),
  constraint offboarding_cases_state_chk
    check (state in ('started','handover','interview','done','cancelled')),
  constraint offboarding_cases_reason_chk
    check (reason_code in ('own_wish','probation_failed','performance','redundancy',
                           'no_show','end_of_contract','transfer_out','other'))
);
create index idx_offboarding_cases_tenant on offboarding_cases (tenant_id, state);
create unique index uq_offboarding_case_active
  on offboarding_cases (tenant_id, user_id) where state not in ('done','cancelled');
```

## 4. Состояния и переходы

### 4.1 Этап человека

```
(нет)      ──найм из воронки──→ onboarding
(нет)      ──ручное заведение──→ onboarding
onboarding ──завершён онбординг──→ integration
integration ──завершена интеграция──→ training      (рабочее состояние по умолчанию)
training   ──назначена аттестация──→ attestation
attestation ──аттестация завершена──→ training
любой      ──запущен офбординг────→ offboarding
offboarding ──завершён────────────→ (архив, доступ закрыт)
offboarding ──отменён─────────────→ предыдущий этап
```

[решение] `recruiting` — этап только для `kind='candidate'`; сотрудник в него не попадает
никогда. При найме человек сразу получает `onboarding` (`docs/28` §7.6).

[решение] `training` — состояние по умолчанию для работающего сотрудника. Иначе пришлось бы
придумывать девятый этап «работает», а он ничего не добавляет.

### 4.2 Офбординг

| Из | В | Кто | Условие | Последствие |
|---|---|---|---|---|
| — | `started` | `offboarding.start` | указаны причина и последний рабочий день | человек переходит в этап `offboarding`, назначаются курсы офбординга |
| `started` | `handover` | автоматически | создан чек-лист передачи дел | — |
| `handover` | `interview` | автоматически | чек-лист закрыт | назначается выходное интервью, если включено |
| `interview` | `done` | `offboarding.complete` | наступил последний рабочий день | доступ закрывается, см. §7.7 |
| любое | `cancelled` | `offboarding.start` | человек остаётся | этап возвращается к прежнему, назначения офбординга снимаются |

[решение] Завершение офбординга **не удаляет человека и не обезличивает его**. История
обучения сотрудника — доказательство того, что инструктаж проводился, и она нужна дольше,
чем сам сотрудник работает. Обезличивание делается отдельной операцией по запросу субъекта
персональных данных (`docs/38` §7, `gdpr.erase`), а не увольнением.

## 5. Экраны

### 5.1 Каталог с разрезом по этапам — `/courses`

К существующему каталогу базового ТЗ добавляется фильтр «Етап» (мультивыбор из включённых
этапов) и режим группировки «За етапом». Курсы без этапа собираются в группу «Без етапу»
с подсказкой администратору: «N курсів без етапу — їх не видно у розрізі по етапах».

Пустое состояние группы: «У цьому етапі ще немає курсів» + «Створити курс».

### 5.2 Настройка этапов — `/settings/lifecycle`

Список восьми этапов: код (серым, нередактируемый), название (редактируемое), иконка, цвет,
порядок, переключатель «Увімкнено», счётчик курсов и людей в этапе.

Возможности этапа показаны **только для чтения**, в виде списка значков с подсказками
(«Прогрес · Дедлайн · Оцінка · Сертифікат»). Рядом текст: «Набір можливостей етапу задає
платформа. Щоб змінити — зверніться до підтримки.»

Выключение этапа: если в нём есть курсы или люди, показывается предупреждение со списком
и блокируется до переноса — `409 lifecycle_stage.in_use`.

### 5.3 Карточка человека — блок «Етап»

В шапке карточки — текущий этап с датой входа («Онбординг, з 14.03»). Назначенное обучение
группируется по этапам (см. `docs/38` §6). Группа этапа с выключенным `progress` показывает
плоский список без процентов и дедлайнов — так же, как это сделано на эталоне для базы знаний.

### 5.4 Офбординг — `/offboarding`

Список активных случаев: человек, точка, должность, причина, последний рабочий день,
состояние, прогресс чек-листа, ответственный. Фильтры: точка, состояние, период,
причина. Карточка случая: чек-лист передачи дел, выходное интервью, кнопка «Завершити».

Пустое состояние: «Активних звільнень немає».

### 5.5 Сводка по этапам — `/reports/lifecycle`

Плитки: сколько людей в каждом этапе сейчас, среднее время в этапе, сколько застряло дольше
нормы. Разрезы: точка, подразделение, должность.

## 6. Формы

### 6.1 Присвоение этапа курсу (в карточке курса)

| Поле | Контрол | Обяз. | Подсказка | Валидация | Текст ошибки (uk) |
|---|---|---|---|---|---|
| Етап | селект из включённых | нет | «Визначає, які можливості доступні цьому курсу» | этап включён у тенанта | «Етап вимкнено в налаштуваннях» |

При смене этапа на курсе с завершёнными прохождениями — модальное предупреждение:

звітність. Змінити?» с кнопками «Змінити» / «Скасувати».

## 7. Правила и алгоритмы

1. **Единая точка проверки возможности.** В коде существует одна функция
   `stageCan(courseId, capability): boolean`. Любая ветка поведения, зависящая от этапа,
   проходит через неё. Проверка `if (stage.code === 'knowledge')` запрещена и ловится
   contract-тестом (`docs/07-stages.md`, сквозная проверка: `grep` по кодам этапов в
   бизнес-логике даёт пустой результат вне справочника).
2. **Автоматическая простановка этапа.** Курс получает этап, если: создан из шаблона этапа;
   создан внутри группы каталога, у которой задан этап по умолчанию; назначен правилом
   автоматизации, привязанным к этапу. Во всех прочих случаях этап проставляет человек.
3. **Курс без этапа.** Работает с полным набором возможностей (все `true`), как обычный курс
   каталога базового ТЗ. Это гарантирует, что ничего из базового ТЗ не ломается.
4. **Смена этапа у курса с прохождениями.** Разрешена только администратору и только с
   подтверждением. Уже созданные назначения **не пересчитываются**: их параметры зафиксированы
   в момент создания (инвариант 1). Новые назначения получают новые правила. `stage_locked`
   выставляется в `true` после первого завершённого прохождения и снимается только оператором.
5. **Возможность и назначение.** Форма назначения читает возможности этапа и скрывает
   неприменимые поля. Если возможность выключена, соответствующий ключ `params` не
   сохраняется вовсе — а не сохраняется со значением по умолчанию. Иначе выключенный дедлайн
   всплывёт в отчётах как «срок не соблюдён».
6. **Переход человека между этапами.** Автоматический переход происходит, когда завершены
   **все** обязательные назначения текущего этапа. Необязательные назначения переход не
   блокируют. Ручной перевод доступен HR с указанием причины.
7. **Завершение офбординга.** Транзакционно: `state='done'`; `access_revoked_at=now()`;
   все активные сессии человека завершаются; незавершённые назначения переводятся в
   `НЕ ПРИЗНАЧЕНО` с пометкой «звільнення»; человек исключается из лимита активных
   пользователей (`docs/35`); запись остаётся в системе; в `audit_log` пишется
   `offboarding.completed`. Данные не стираются.
8. **Возврат уволенного.** Повторный найм того же человека не создаёт новую запись: снимается
   `access_revoked_at`, создаётся новое `user_placements`, новый `employee_lifecycle_state`
   с этапом `onboarding`. Прошлая история видна отдельным блоком «Попередній період роботи».
9. **Кандидат и этапы.** Кандидату можно назначить только курсы этапов с
   `applies_to_candidate = true` (по умолчанию это `recruiting` и `psychological`). Попытка
   назначить иной — `422 lifecycle.not_for_candidate`.
10. **Выключенный этап.** Курсы выключенного этапа не видны в каталоге и не назначаются, но
    уже идущие прохождения продолжаются до завершения. Выключение — не удаление.
11. **Норма времени в этапе.** У этапа задаётся ожидаемая длительность в днях (по умолчанию:
    онбординг 14, интеграция 30, аттестация 7, офбординг 14). Превышение попадает в отчёт
    «застрягли» и в дайджест руководителю, но ничего не блокирует.

## 9. Отчёты и выгрузки

1. **Люди по этапам.** Этап · человек · точка · должность · дней в этапе · прогресс ·
   превышение нормы. Фильтры: точка, подразделение, должность, этап, период.
2. **Скорость прохождения этапов.** Этап · медиана дней · 90-й перцентиль · норма ·
   доля превысивших. Разрез по точкам — это прямой показатель качества наставничества.
3. **Офбординг.** Причина · число · доля · средний стаж уволившихся · доля прошедших
   выходное интервью. Разрез по точкам и по сроку работы (до 3 мес. / 3–12 / больше года):
   уход в первые три месяца — это дефект найма или онбординга, и отчёт должен это показывать.
4. **Курсы без этапа.** Список для администратора, чтобы закрыть пробел.
5. **Выгрузка результатов выходных интервью** — агрегированно; ответы конкретного человека
   доступны только HR и только если опрос не анонимный.

## 12. Крайние случаи

1. **Человек переведён на другую точку посреди онбординга.** Этап сохраняется, назначения
   остаются; добавляются курсы онбординга новой точки, если они отличаются. Счётчик дней
   в этапе не обнуляется.
2. **Курс относится к двум этапам по смыслу** (например, вводный инструктаж нужен и при
   онбординге, и при интеграции). Этап у курса один; для второго сценария курс кладётся в
   библиотеку (`docs/31`) и переиспользуется. Множественная привязка не вводится осознанно:
   она сразу ломает отчёт «люди по этапам».
3. **Офбординг запущен ошибочно.** Отмена до `done`; после `done` — повторный найм по
   правилу 7.8.
4. **Человек уволен, но у него есть незакрытая проверка в очереди.** Работа остаётся в
   очереди и проверяется: результат нужен для статистики и для возможного повторного найма.
5. **Выключен этап, в котором люди сейчас находятся.** Блокируется (§5.2). Выключить можно
   только этап без активных людей и курсов.
6. **Кандидат нанят, а курс рекрутингового этапа не завершён.** Незавершённое назначение
   остаётся и доступно: у человека теперь `kind='employee'`, но назначение живёт по своим
   правилам. В отчёте по этапам он числится на онбординге.
7. **Последний рабочий день в прошлом при запуске офбординга.** Разрешено в пределах 30 дней
   назад (частая ситуация: человек ушёл, оформляют задним числом). Доступ закрывается сразу.
8. **Тенант хочет девятый этап.** Не поддерживается. Порядок: обращение оператору платформы,
   который оценивает, нужен ли новый код всем тенантам. Это осознанное ограничение — иначе
   через полгода этапов станет тридцать, а отчётность перестанет сравниваться между точками.

## 13. Критерии приёмки

1. **Дано** курс этапа «База знань», **коли** ему создают назначение, **тоді** в форме нет
   полей срока, попыток и проходного балла, а в сохранённом `params` нет соответствующих
   ключей.
2. **Дано** курс этапа «База знань» назначен человеку, **коли** открывается карточка человека,
   **тоді** курс показан в плоском списке с датой назначения, без процента и без дедлайна.
3. **Дано** курс без этапа, **коли** ему создают назначение, **тоді** доступны все поля,
   поведение совпадает с базовым ТЗ до внедрения этого документа.
4. **Дано** этап «Психологічні тести», **коли** по его курсу завершено прохождение,
   **тоді** оценка не выставляется и рейтинг человека (`docs/38`) не изменяется.
5. **Дано** кандидат, **коли** ему пытаются назначить курс этапа «Онбординг», **тоді**
   `422 lifecycle.not_for_candidate`, назначение не создано.
6. **Дано** исходный код бизнес-логики, **коли** выполняется `grep` по строкам
   `'knowledge'`, `'attestation'`, `'offboarding'` вне справочника и миграций, **тоді**
   совпадений нет — все ветки идут через `stageCan()`.
7. **Дано** человек завершил все обязательные назначения этапа «Онбординг», **коли**
   отработала `lifecycle.advance`, **тоді** текущий этап стал «Інтеграція», прежняя запись
   получила `left_at`, `is_current` осталась ровно одна.
8. **Дано** этап «Атестація», в котором 3 курса, **коли** администратор его выключает,
   **тоді** `409 lifecycle_stage.in_use` со списком курсов.
9. **Дано** запущен офбординг с последним рабочим днём вчера, **коли** ответственный нажимает
   «Завершити», **тоді** сессии человека завершены, активных назначений не осталось, лимит
   активных пользователей уменьшился, запись человека и вся история обучения сохранены.
10. **Дано** офбординг завершён 10 дней назад, **коли** того же человека нанимают снова,
    **тоді** используется та же запись `users`, видны оба периода работы, новый этап —
    «Онбординг».
11. **Дано** курс с завершёнными прохождениями, **коли** администратор меняет ему этап без
    подтверждения, **тоді** `409 course.stage_locked`.
12. **Дано** новый тенант, **коли** он создан, **тоді** у него ровно восемь этапов со
    значениями возможностей из таблицы §3.3.

## 14. Сверено с эталоном

Снято с Sintegrum:
- Перечень категорий жизненного цикла и то, что меню строится вокруг них (`/tracks/<category>`).
- Разное поведение категорий: отсутствие ИИ-генерации у психологических тестов и базы знаний;
  плоский список без прогресса и дедлайна у базы знаний в карточке сотрудника.
- Наличие офбординга как самостоятельной категории (на эталоне пустой).
- Группировка назначенного обучения по категориям в карточке сотрудника.

Снято с LMS Collaborator (базовое ТЗ):
- Свободный каталог с пользовательскими категориями, программы и траектории поверх.
- Правило «правила прохождения — в назначении», которое здесь сохранено без изменений.

Решением Lola, не снятым ни с одного эталона, являются: модель `capabilities`; сокращение
десяти категорий до восьми этапов с выносом библиотеки и обращений в отдельные модули;
разделение этапа курса и этапа человека; запрет на редактирование возможностей тенантом;
процесс офбординга с чек-листом и выходным интервью.

## 15. Гипотезы и принятые по ним решения

**Г-33.1. Полный перечень поведенческих отличий категорий на эталоне.** Снято выборочно:
подтверждено отсутствие ИИ-генерации у двух категорий и отсутствие прогресса у базы знаний;
остальные отличия не перебирались по каждой категории.
[гипотеза] Отличий больше, и они того же рода — отсутствие отдельных возможностей.
[решение] Модель `capabilities` спроектирована расширяемой: новое отличие добавляется ключом
в jsonb и строкой в таблицу §3.3, без изменения кода вне `stageCan()`.
*Чем проверяется:* пройти на эталоне по всем восьми категориям и сравнить состав кнопок на
экране списка и в форме создания.

**Г-33.2. Есть ли на эталоне явное состояние человека «на этапе».** Не найдено: в карточке
сотрудника назначенное сгруппировано по категориям, но отдельного поля «текущий этап» не видно.
[гипотеза] Состояние не хранится, а выводится из наличия незавершённых назначений категории.
[решение] Для Lola состояние хранится явно (§3.5). Вывод из назначений ломается в первом же
реальном случае — сотрудник с параллельными назначениями двух этапов.
*Чем проверяется:* открыть на эталоне карточку сотрудника с назначениями из двух категорий и
посмотреть, показывает ли система один «текущий» этап.

**Г-33.3. Как на эталоне устроен офбординг.** Категория есть, треков в ней ноль — процесс не
наблюдался.
[гипотеза] Это обычная категория треков, без отдельного процесса увольнения; передача дел и
закрытие доступа делаются вне системы.
[решение] Для Lola офбординг — не только курсы, но и процесс (`offboarding_cases`, §3.6):
закрытие доступа и освобождение лимита должны быть операцией продукта, иначе тенант платит
за уволенных и они продолжают получать уведомления.
*Чем проверяется:* создать на эталоне трек в категории «Офбординг» и посмотреть, появляются
ли дополнительные поля и действия, которых нет в других категориях.

**Г-33.4. Норма времени на этап.** На эталоне не найдена.
[гипотеза] Не задаётся; «застрявших» отслеживают вручную.
[решение] Вводим норму с значениями по умолчанию (правило 7.11), но только как сигнал —
ничего не блокирует. Значения взяты из практики линейного найма и подлежат уточнению на
первом тенанте.
*Чем проверяется:* сопоставить фактические медианы по Каппі через квартал после запуска и
скорректировать значения по умолчанию.

**Г-33.5. Можно ли на эталоне добавить свою категорию.** Кнопки добавления категории не
обнаружено, в отличие от статусов кандидата, где такая кнопка есть.
[гипотеза] Категории фиксированы платформой.
[решение] То же для Lola (§3.2, §12.8), с явным обоснованием ограничения.
*Чем проверяется:* поискать на эталоне действие добавления категории в разделе настроек.
