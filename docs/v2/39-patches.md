# Lola LMS — ТЗ. 39. Патчи к базовому ТЗ

## Назначение

Пакет `lola-spec-v2` добавляет одиннадцать модулей. Часть из них не может работать, пока в
базовом ТЗ не изменены существующие документы: в каталоге людей появились кандидаты, в
каталоге курсов — этапы, в очереди проверки — делегирование. Этот документ перечисляет **все**
такие изменения точечно: какой документ, какой раздел, что заменить и почему.

Правило применения: патч применяется к базовому документу правкой **с пометкой-исправлением**,
а не тихой заменой. В базовом документе остаётся строка вида
`> [исправлено пакетом v2, П-16.1] Ранее: «…». Причина: …`.

Патчи отсортированы по номеру базового документа. Приоритет: **блокирующий** — без него
пакет ломает существующее поведение; **обязательный** — без него новый модуль неполон;
**желательный** — улучшение, можно отложить.

## П-16. `16-people.md` — кандидаты в реестре людей

**Приоритет:** блокирующий. Это самый важный патч пакета.

**П-16.1.** Все выборки людей получают явный фильтр по `users.kind`.
До пакета `users` содержала только сотрудников, и выборки вида `select … from users where
tenant_id = …` были корректны. После миграции, вводящей `kind`, те же выборки начнут
возвращать кандидатов: в списке сотрудников, в адресатах рассылки, в отчётах по штату, в
подсчёте лимита активных пользователей, в выгрузках.

Требование: ни одна выборка людей не выполняется без явного `kind`. Проверяется сквозной
проверкой П-07.2. Рекомендуемая реализация — два представления или два репозиторных метода
(`employees()`, `candidates()`), а не ручной фильтр в каждом запросе.

**П-16.2.** Карточка человека дополняется четырьмя блоками из `38-people-extensions.md`:
лента активности, заметки, документы, нормы отсутствий; и блоком «Етап» из `33`.

**П-16.3.** В список сотрудников добавляется колонка рейтинга (`38` §3), с оговорками:
не выгружается по умолчанию, не может быть единственным условием массового действия,
публичной доски лидеров нет.

**П-16.4.** Руководитель человека определяется функцией `resolveManager()` из `32` §7.8;
`locations.manager_id` понижается до резервного источника. Переключение — по флагу тенанта
`org_structure_is_source_of_truth`.

(`35` для лимитов и аддонов, `29` для квоты ИИ в вакансиях).

**Отдельное правило:** уведомления кандидатам (`28` §8) идут **вне** тихих часов тенанта, но
внутри разумного окна 09:00–20:00 по локальному времени кандидата. Тихие часы настроены под
сотрудников одной сети; кандидат к этой сети не принадлежит.

**Отдельное правило:** дайджест руководителю (`23` §13.2.1) теперь получает адресата из
`resolveManager()` (`32` §7.8), а не из `locations.manager_id`.

## П-25. `25-multitenancy.md` — лимиты и публичный контур

**Приоритет:** обязательный.

> [исправлено, `43` §5] Ранее в п. 1: «одиннадцать осей вместо трёх». Фактически
> `tenant_limits` уже имеет **шесть** явных колонок (`users, storage_gb, sms_per_month,
> api_per_minute, webhooks, active_jobs`), а не три; `jsonb`-хранилище лимитов пакет не
> находит в БД. Решение `44` В-5 доводит их до одиннадцати явными колонками (пять новых:
> `candidates`, `ai_generate_ops`, `ai_review_ops`, `ai_interview_ops`, `export_rows`), с
> `jsonb` только для нетарифной оси `telegram_out`.

**Что:**
1. Оси лимитов заменяются перечнем из `35` §7.1 — **одиннадцать осей вместо шести**, явными
   колонками `tenant_limits` (см. `44` В-5), а не `jsonb`.
2. Правило «обучение никогда не останавливается лимитами» сохраняется дословно и
   распространяется на новые оси: при исчерпании ИИ-лимита проверка деградирует в ручную,
   при исчерпании хранилища сдача видеоответа сохраняется на устройстве и досылается (`34` §7).
3. Добавляется раздел о публичном контуре `/api/v1/public/*` (`29` §10, уже работает —
   `43` §5): как он проходит изоляцию тенанта, если сессии нет. Тенант определяется по токену
   ссылки (вакансии, тайного гостя и т. д.), и дальше запрос идёт через `withTenant()` с ролью
   минимальных прав, взятой из строки токена, а не из тела запроса.
