## 1. Единица работы и правила

**PR — это единица.** Размер подобран так, чтобы `pnpm check` (lint → typecheck →
`test:quiet` → `e2e:quiet`) проходил на каждом, а работа влезала в **1–3 сессии агента**.
Ветка — `<область>-<номер>` по правилу `CLAUDE.md`, с префиксом пакета: `v2-<область>-NN`,
где `NN` — номер PR из этого документа.

**Цикл PR** — `HANDOFF` §5, без отклонений: ветка от актуального `main` → миграция → сервис
в `server/services` → контракт zod в `shared/schemas` → тонкий эндпоинт → тесты → i18n и
токены → гейт → PR → строка в `46-progress.md`.

**Условия входа** PR — что должно быть смержено в `main` и какой факт проверяется командой
перед началом. **Условия выхода** — что должно стать правдой после мержа; они и есть вход
для зависимых PR. Оба обязательны: PR без них в работу не берётся.

**Модель исполнителя** — по таблице `CLAUDE.md` «Экономия контекста», не по умолчанию.
Opus — схема, миграции, сервис с бизнес-логикой, стык модулей, разбор противоречий.
Sonnet — документы, i18n, вёрстка по готовому мокапу, тесты по готовому образцу, скрипты, CI.

**Оценка** — в сессиях агента: 1 сессия ≈ ветка от начала до зелёного гейта без
переключения контекста. Сумма по плану — §7.

## 5. Миграции: нумерация и параллельные ветки

**Нумерация.** Пакет начинается с `0054`. Стиль имени — `NNNN_v2_<область>_<что>.sql`.
Номера в §4 — **планируемые**: они верны, если PR мержатся в порядке этого документа.

**Правило для параллельных дорожек.**

1. Номер файла и `when` в `meta/_journal.json` назначаются **при rebase перед созданием PR**,
   а не при создании ветки. До этого момента в ветке лежит миграция с временным номером.
2. Перед `gh pr create` — обязательный `git fetch && git rebase origin/main` (правило
   `CLAUDE.md`). Если в `main` появилась миграция с большим номером, своя **переименовывается**
   в `max+1`, а `when` выставляется в `max(when) + 1000`.
3. **`when` обязан строго возрастать.** На накаченной БД drizzle сравнивает `when` с
   максимальным применённым и **молча пропускает** миграцию с меньшим значением — она не
   упадёт, она не выполнится. Ловится `tests/unit/migrations-journal.spec.ts` (PR-01).
4. Нарушение уже существует в `main` и чинится в PR-01: `0053_spec_development_goal_tree`
   имеет `when` меньше, чем `0052`.
5. Параллельные ветки **не держат миграцию дольше одного рабочего дня**: чем дольше ветка
   живёт с миграцией, тем дороже перенумерация. Если PR завис — миграция выносится в
   отдельный первый PR, а логика доезжает следующим.
6. Две ветки **не трогают одну таблицу** одной миграцией. Пары, за которыми следить:
   `users` (PR-04 → PR-13 → PR-15 → PR-34 → PR-35), `media_assets` (PR-11 → PR-12),
   `tenant_limits` (PR-08), `workshop_submissions` (PR-19 → PR-20 → PR-21),
   `lessons` (PR-25). Все — внутри одной дорожки, поэтому последовательны по построению.

**Какие PR можно вести одновременно** (не пересекаются ни по файлам, ни по миграциям):

| Окно | Параллельно |
|---|---|
| после PR-01 | PR-02, PR-03, PR-04 |
| после PR-04 | PR-05 (Т1), PR-08 (Т2), PR-11 (Т3), PR-18 (Т5), PR-21 (Т5) |
| после PR-12 | PR-13 (Т4), PR-23 (Т6), PR-25 (Т6), PR-30 (Т7), PR-32 (Т7) — до **четырёх** дорожек |
| после PR-19 | PR-20, PR-22, PR-31 |

### 6.2 Правило разрезания: что делать, если PR не влезает

Признак «не влезает»: гейт не сходится за три сессии, либо `pnpm check` требует правок в
файлах, не названных в описании PR.

Резать в этом порядке — первый применимый способ:

1. **Отделить миграцию от логики.** Первый PR — только DDL + RLS + индексы + контрактные
   тесты 1–3 на новые таблицы; второй — сервисы и эндпоинты. DDL без потребителей безопасен
   и проходит гейт сам по себе. Не применимо к PR-04: там миграция и патч связаны жёстко.
2. **Отделить экран от сервера.** Сервер с тестами — один PR, вёрстка по мокапу — второй,
   sonnet. Обратный порядок запрещён: «сервер считает, клиент показывает».
3. **Отделить фоновую задачу.** `*.purge`, `*.sweep`, `*.archive`, агрегаты — отдельным PR
   после основного; до него данные копятся, ничего не теряется.
4. **Отделить отчёт.** Отчёт на `reportFrame` — всегда отдельный PR, sonnet.
5. **Отделить второй сценарий сущности.** Например, `vacancy_publications` от `vacancies`
   (так и сделано: PR-15 / PR-17).

**Чего при разрезании делать нельзя:** разрывать пары из §2; вводить колонку, которую никто
не читает, «чтобы не переделывать миграцию»; переносить проверку инварианта в следующий PR.
Если разрез требует нарушить §2 — PR не режется, а **переносится позже**, а зависимый
переупорядочивается.

**Обратное правило — если PR слишком мал** (меньше сессии): объединять разрешено только
внутри одной дорожки и только если суммарно не выходит за три сессии.
