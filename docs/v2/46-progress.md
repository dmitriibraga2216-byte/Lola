### Четыре дорогих для отката решения

1. **`review_queue_items` — полноценная таблица**, источник истины о состоянии очереди;
   содержание работы остаётся в источнике; `workshop_submissions.reviewer_id/claimed_at/sla_due_at`
   понижаются до зеркала и удаляются через один PR. Решило наличие идентичности: делегирование,
   события SLA и статистика проверяющего ссылаются на элемент очереди, а у строки, собранной
   запросом, устойчивого идентификатора нет.
2. **`media_assets`: переименовать, а не заводить рядом.** `uploaded_by` → `owner_user_id`,
   `checksum` → `checksum_sha256`. Решил замер: `checksum` — мёртвая колонка (0 чтений, 0 записей),
   `uploaded_by` — одна запись в продакшн-коде и ноль чтений. Факт «кто загрузил» переезжает
   в `audit_log` событием `media.upload` (сегодня `media.ts` не пишет аудит ни разу).
3. **Лимиты остаются явными колонками**, 6 → 11 осей; `jsonb` только для нетарифных;
   `plans` остаётся с PK по `code`, `plan_prices.plan_id` → `plan_code`. Решили пять мест
   сырого SQL, где потребление сравнивается с лимитом (`usage.ts:33`, `platform.ts:74/96/198/234`):
   это счёт клиенту, и опечатка в ключе jsonb там читается как «без обмежень».
4. **Фильтр по `users.kind` — три слоя:** репозиторные методы + тест-сканер по исходникам
   с поимённым allowlist + канареечный кандидат в посеве, всё в одном PR с миграцией.
   Представления отвергнуты (ломают `drizzle-kit generate`, `rls.spec.ts`, `schema-parity.spec.ts`
   и рискуют обойти RLS без `security_invoker`), ESLint-правило отвергнуто (закрывает 60 из 148
   мест и ровно не закрывает счётчик биллинга — он написан сырым SQL).
   Измеренная цена уточнена: **≈148 точек ревизии**, из них **≈50 списочных**.

### Ключевые находки

1. **Блокер №1 из README снят.** `scales` и `scale_levels` существуют, работают и уже
   используются опросами, чек-листами и компетенциями (Р-4, П-20). «Переносить минимальный
   срез вперёд» больше не нужно — вопрос уходит с повестки фазы 1.
2. **Расширения `ltree` и `vector` уже созданы** в `0000_youthful_warhawk.sql` (Р-5).
   Миграция `0004_extensions.sql` из `40` §5 отменяется. Единственное место, где пакет падал
   бы на чистой базе на первом файле, закрыто само.
3. **`review_queue_items` не существует вообще** — ни таблицей, ни представлением, ни
   матвью (во всей схеме `public` ноль представлений). Очередь собирается запросом в
   `server/services/queue.ts`. Р-3 не закрыт, а обострился: «повышение витрины до таблицы»
   оказалось созданием с нуля, и DDL надо внести в `docs/02`, где таблицы нет вовсе.
4. **Цена П-16.1 измерена:** ≈98 мест обращения к `users` (59 × `from(users)` в 26 файлах
   `server/services` + 39 сырых `from users` в SQL). Рекомендация Р-9 — «поимённый перечень
   выборок вместо общего правила» — из желательной становится обязательной.
5. **Две таблицы пакета дублируют существующие:** `org_structure_conflicts` = `org_conflicts`,
   `person_notes` = `user_notes`. Обе превращаются в `alter table`. Вместе с отменённой
   `storage_quota_addons` (Р-6) состав пакета: **70 новых таблиц вместо 73**.
6. **Публичный контур уже работает** — `/api/v1/public/{guest-page,signup,mystery/[token]}`,
   изоляция по токену через `withTenant` (`server/services/mystery.ts:86`). Механизм из
   П-25.3 не проектировать, а описать. Путь пакета `/api/public/v1` не существует и не
   должен: Nitro задаёт префикс деревом каталогов.
7. **Пять пунктов `41` §8 репозиторий решил молча, и не в пользу пакета:**
   `validation_failed` (не UPPER_SNAKE), `forbidden` (одно написание вместо пяти),
   `media.too_big` (третий вариант, в §8.2.4 не рассмотренный), единый `limit_exceeded`,
   окно частотных ограничений — на токен интеграции (`apiTokens.ts:60`). Править надо
   документы пакета, а не код.
8. **Две посылки пакета о существующей схеме неверны:** лимиты — не `jsonb` `overrides`, а
   явные колонки (осей шесть, а не три, как пишет П-25.1), и `plans` имеет PK по `code` без
   `id`. Формула эффективного лимита `35` §7.3 и FK `plan_prices.plan_id` переписываются.
